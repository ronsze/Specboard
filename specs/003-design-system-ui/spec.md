# Feature Specification: 디자인 시안 적용

**Feature Branch**: `003-design-system-ui`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "디자인 시안 적용 feature. 시안 파일은 docs/Specboard-selection.pdf(10쪽)이고 요구사항 배경은 docs/design-brief.md다. 범위: (1) 디자인 토큰과 공용 컴포넌트를 도입하고 기존 모든 화면(로그인, 홈, 입력 목록, 승인 대기, 멤버 관리, spec, 버전 이력)을 시안대로 다시 만든다. 라이트 모드 기본, 시안의 다크 모드 제안을 따른다. 모든 상태는 색만이 아니라 아이콘과 글자로도 구분하고 키보드로 조작 가능해야 한다. 권한 없는 동작은 비활성이 아니라 보이지 않게 하고 상단의 내 역할 배지로 설명한다. (2) 시안이 요구하는 데이터 보강: 입력 번호(IN-n), spec 항목 종류별 안정 번호(D-n, R-n)와 처음 생긴·마지막으로 바뀐 버전 표시, 보드 단위 승인 대기 화면과 상단 대기 개수 배지, 홈의 feature별 요약, 입력 목록 필터와 긴 본문 펼치기, 되돌리기 전 영향 미리보기, 비교 화면의 A/B 선택·변경 없는 항목 숨김·단어 단위 변경 표시, 갱신 중·실패·확정 안내 문구, 403·404·빈 상태 화면. (3) 출처 인용 발췌: 출처를 펼치면 원문 중 해당 문장을 강조해 보여주고 원문 전체 보기로 이동한다. 인용 발췌는 AI가 제시하되 서버가 원문에 실제로 있는지 확인하고, 없으면 발췌 없이 원문만 보여준다. 범위 밖: 입력의 회의 제목 필드, 질문에 답이 될 만한 입력 연결 힌트, 충돌 경고 표시, 모바일 전용 시안(반응형은 spec 보기와 입력 제출 두 화면만 최소 지원), 알림, 가입."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - spec 화면에서 항목, 출처, 미결 질문을 한눈에 본다 (Priority: P1)

팀원이 feature의 spec 화면을 열면 결정과 요구사항이 번호(D-1, R-2 등)와 함께 목록으로 보이고, 각 항목에서 근거가 된 입력을 바로 펼쳐 볼 수 있다. 오른쪽(좁은 화면에서는 항목 위)에는 미결 질문이 항목과 시각적으로 구별되어 나타난다. 화면 상단에는 현재 버전, 상태(최신, 갱신 중, 갱신 실패, 확정), 반영 대기 입력 안내가 보인다.

**Why this priority**: 이 제품의 핵심 가치(출처가 달린 spec)가 전달되는 화면이다. 이 화면만 시안대로 완성해도 제품의 신뢰 메시지가 드러난다.

**Independent Test**: 항목, 출처, 미결 질문, 확정 상태가 있는 spec을 열어 번호, 출처 펼침, 질문 영역, 상태 안내가 시안과 같은 구조로 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** spec에 결정 2개와 요구사항 3개가 있다, **When** spec 화면을 연다, **Then** 항목마다 종류 표시와 종류별 번호(D-1, D-2, R-1, R-2, R-3)가 보이고, 결정·요구사항 개수가 요약된다.
2. **Given** 항목에 출처가 2개 있다, **When** "출처 2"를 누른다, **Then** 항목 바로 아래에 근거 입력 목록이 펼쳐지고 각 출처의 입력 번호, 종류, 제출자, 제출 시각, 승인 상태가 보이며, 한 번 더 눌러 원문 전체를 볼 수 있다.
3. **Given** 열린 질문 2개와 해소된 질문 1개가 있다, **When** spec 화면을 연다, **Then** 미결 질문 영역에 열림·해소 개수가 요약되고, 해소된 질문에는 답과 "답이 된 입력"이 표시된다.
4. **Given** 항목이 v3에서 처음 생겼고 v7에서 마지막으로 바뀌었다, **When** 항목을 본다, **Then** "v3부터"와 "v7에서 변경"이 표시되고, 바뀌지 않은 항목에는 "변경" 표시가 없다.
5. **Given** spec 상태가 갱신 중, 갱신 실패, 확정, 승인된 입력 없음 중 하나이다, **When** 화면을 연다, **Then** 상태에 맞는 안내(진행 안내, 마지막 성공 버전은 그대로 보임과 입력 손실 없음, 확정자·시각, 승인 대기 입력 안내)가 보이고 상태는 색뿐 아니라 아이콘과 글자로도 구분된다.
6. **Given** 승인되었으나 아직 반영되지 않은 입력이 2개 있다, **When** spec 화면을 연다, **Then** "다음 갱신에 반영됩니다" 안내와 입력 목록으로 가는 링크가 보인다.
7. **Given** 관리자가 아닌 사용자이다, **When** spec 화면을 연다, **Then** 확정·재시도 같은 관리자 전용 동작은 화면에 나타나지 않는다.

### User Story 2 - 입력 화면에서 번호, 상태, 원문을 읽기 쉽게 보고 걸러 본다 (Priority: P1)

멤버와 관리자가 feature의 입력 화면에서 입력을 제출하고 목록을 본다. 입력 카드에는 입력 번호(IN-7), 종류, 상태, 제출자·시각, 원문이 그대로 보이고, 긴 회의록은 접혀 있다가 펼칠 수 있다. 목록 위의 필터로 전체, 내 대기, 반영 대기, 반려 입력만 골라 볼 수 있다.

**Why this priority**: 모든 입력이 시작되는 화면이며, 번호와 필터가 있어야 spec 항목의 출처를 입력 목록에서 다시 찾을 수 있다.

**Independent Test**: 상태가 다른 입력 여러 개와 긴 회의록 하나가 있는 feature에서 필터와 펼치기, 제출 폼을 확인한다.

**Acceptance Scenarios**:

1. **Given** 입력이 여러 개 있다, **When** 입력 화면을 연다, **Then** 각 카드에 입력 번호, 종류, 상태(아이콘과 글자), 제출자, 제출 시각이 보이고 원문은 편집 없이 그대로 보인다.
2. **Given** 본문이 긴 회의록이다, **When** 목록을 본다, **Then** 처음 몇 줄만 보이고 "펼치기"와 전체 글자 수가 표시되며, 펼치면 전체가 보인다.
3. **Given** 승인된 입력이다, **When** 카드를 본다, **Then** "v7에 반영됨" 또는 "반영 대기"가 표시된다. 반려된 입력에는 "spec에 쓰이지 않음"과 반려 사유(반려자·시각 포함)가 눈에 띄게 보인다.
4. **Given** 멤버 본인의 대기 입력이다, **When** 목록을 본다, **Then** "나와 관리자에게만 보임" 안내가 표시된다.
5. **Given** 필터 "내 대기"를 선택한다, **When** 목록을 본다, **Then** 내가 낸 대기 입력만 보이고, 각 필터 버튼에는 해당 개수가 표시되며, 결과가 없으면 빈 상태 안내가 보인다.
6. **Given** 제출 폼이다, **When** 본문을 입력한다, **Then** 현재 글자 수와 한도(50,000)가 보이고, 제출 후 흐름(대기 → 관리자 승인 → 다음 갱신에 spec 재료로 사용) 안내가 보인다.
7. **Given** 열람자이다, **When** 입력 화면을 연다, **Then** 제출 폼은 나타나지 않는다.

### User Story 3 - 관리자가 보드 전체의 승인 대기를 한 화면에서 처리한다 (Priority: P2)

관리자는 화면 상단의 "승인 대기 N" 배지로 보드 전체의 대기 입력 수를 항상 볼 수 있고, 누르면 보드 안의 모든 feature의 대기 입력이 한 목록으로 나온다. 목록에서 feature로 이동하지 않고도 승인하거나, 사유를 적어 반려한다.

**Why this priority**: 관리자의 승인 업무를 크게 줄이지만 입력·spec 화면 뒤에 필요하다.

**Independent Test**: 서로 다른 두 feature에 대기 입력이 있는 보드에서 관리자가 한 화면에서 승인과 반려를 처리한다.

**Acceptance Scenarios**:

1. **Given** 보드에 대기 입력이 3개 있다, **When** 관리자가 어느 화면에서든 상단을 본다, **Then** "승인 대기 3" 배지가 보이고, 대기가 0이면 숫자가 보이지 않는다.
2. **Given** 대기 입력이 서로 다른 feature에 속해 있다, **When** 승인 대기 화면을 연다, **Then** 입력마다 어느 프로젝트·feature의 입력인지 링크와 함께 보이고, 오래된 순으로 정렬된다.
3. **Given** 대기 입력이다, **When** 관리자가 "승인"을 누른다, **Then** 목록에서 사라지고 배지의 숫자가 줄어든다.
4. **Given** 대기 입력이다, **When** "반려…"를 누른다, **Then** 반려 사유 입력창(필수, 제출자에게 그대로 보임 안내)이 열리고, 사유가 비어 있으면 확정할 수 없으며, 취소할 수 있다.
5. **Given** 멤버 또는 열람자이다, **When** 화면을 본다, **Then** 승인 대기 메뉴와 배지가 보이지 않는다.
6. **Given** 다른 관리자가 먼저 처리한 입력이다, **When** 이 관리자가 처리를 시도한다, **Then** "이미 처리되었습니다" 안내와 함께 목록이 갱신된다.

### User Story 4 - 홈에서 내 보드와 feature의 상태를 훑어본다 (Priority: P2)

홈에는 내가 속한 보드별로 프로젝트와 feature 목록이 나오고, 각 feature에는 spec 상태(spec 없음, 최신, 갱신 중, 갱신 실패, 확정됨), 최신 버전과 날짜, 반영 대기 입력 수가 한 줄로 요약된다. 보드 제목 옆에는 내 역할이, 관리자에게는 승인 대기 링크가 보인다.

**Why this priority**: 진입점의 가독성을 높인다. 핵심 흐름은 아니라 P2다.

**Independent Test**: 상태가 다른 feature 5개가 있는 보드를 열어 각 feature의 요약이 상태와 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** feature의 spec이 최신 버전 v7이다, **When** 홈을 본다, **Then** "최신", "v7", 날짜가 보이고, 반영 대기 입력이 있으면 그 수가 보인다.
2. **Given** feature에 spec이 아직 없다, **When** 홈을 본다, **Then** "spec 없음"과 승인된 입력이 없다는 안내가 보인다.
3. **Given** 갱신 중, 갱신 실패, 확정된 feature가 있다, **When** 홈을 본다, **Then** 각각 아이콘과 글자로 구분된다.
4. **Given** 사용자가 보드 두 개에 속하고 역할이 다르다, **When** 홈을 본다, **Then** 보드마다 내 역할 배지가 따로 보이고, 관리자 보드에만 승인 대기와 멤버 관리 진입점이 보인다.

### User Story 5 - 버전 이력에서 두 버전을 골라 비교하고, 영향을 확인한 뒤 되돌린다 (Priority: P2)

팀원은 버전 이력에서 두 버전을 선택(A/B)해 추가·삭제·변경을 비교한다. 변경 없는 항목은 기본으로 숨기고 토글로 볼 수 있으며, 변경된 문구는 바뀐 단어가 강조된다. 관리자는 버전 카드에서 "이 버전으로 되돌리기"를 눌러 확인 창에서 영향(빠지는 항목 수, 다시 열리는 질문 수)을 보고 확정한다.

**Why this priority**: 이력과 되돌리기는 AI 자동 갱신의 안전장치이며, 영향 미리보기는 오조작을 줄인다.

**Independent Test**: 버전 3개 이상에서 A/B로 비교하고, 되돌리기 확인 창의 영향 수치가 실제 되돌린 결과와 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 버전이 여러 개 있다, **When** 이력 화면을 연다, **Then** 버전 카드에 번호, 생성 방식(AI 갱신/되돌림), 시각, 근거 입력 번호가 보이고, 현재 버전이 표시되며, 두 버전을 체크해 A/B로 지정할 수 있다.
2. **Given** 두 버전이 선택되었다, **When** 비교 결과를 본다, **Then** 추가·삭제·변경·동일 개수가 요약되고, 각 항목은 기호, 글자, 색으로 구분된다.
3. **Given** 변경된 항목이다, **When** 비교 결과를 본다, **Then** 이전/이후 문구에서 바뀐 단어가 취소선과 밑줄로 강조되고, 새로 붙은 출처가 있으면 "새 출처"로 표시된다.
4. **Given** 같은 버전을 A와 B로 고르려 한다, **When** 선택한다, **Then** 선택이 거부되고 안내가 나온다.
5. **Given** 관리자가 되돌리기를 누른다, **When** 확인 창이 열린다, **Then** "새 버전이 만들어지고 기존 버전은 그대로 남는다"는 안내와 함께 "항목 N개가 빠집니다", "해소된 질문 M개가 다시 열립니다" 같은 영향이 표시되고, 기본 포커스는 취소에 있으며 Esc로 닫힌다.
6. **Given** 확인 창이 열려 있는 동안 spec이 확정되었다, **When** 확정을 누른다, **Then** 되돌리기는 실행되지 않고 확정 상태 안내가 나온다.
7. **Given** 확정 상태의 spec이다, **When** 이력 화면을 본다, **Then** 되돌리기 버튼 대신 확정 중에는 되돌릴 수 없다는 안내와 확정 해제로 가는 링크가 보인다.
8. **Given** 멤버 또는 열람자이다, **When** 이력 화면을 본다, **Then** 되돌리기 버튼은 나타나지 않는다.

### User Story 6 - 출처를 펼치면 근거가 된 문장이 강조되어 보인다 (Priority: P2)

항목의 출처를 펼치면 입력 원문 중 해당 항목의 근거가 된 문장이 강조되어 보이고, "원문 전체 보기"로 입력 전체를 볼 수 있다. 발췌는 AI가 제시하지만 시스템이 원문에 실제로 있는 문장인지 확인한 것만 강조해 보여준다.

**Why this priority**: "이 내용이 정말 어디서 나왔는지"를 가장 직접적으로 보여주는 신뢰 장치다. 다만 구조(출처 패널)가 먼저 필요해 P2다.

**Independent Test**: 긴 회의록에서 나온 항목의 출처를 펼쳐 강조된 문장이 원문에 실제로 있는지 확인하고, 원문에 없는 발췌를 주는 경우 강조 없이 원문만 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 항목이 긴 회의록에서 만들어졌다, **When** 출처를 펼친다, **Then** 해당 문장이 강조되어 인용 형태로 보이고 "원문 전체 보기(IN-7)" 링크가 있다.
2. **Given** 한 항목에 출처가 둘이다, **When** 출처를 펼친다, **Then** 출처마다 각자의 발췌가 따로 보인다.
3. **Given** AI가 준 발췌가 원문에 실제로 없다, **When** 출처를 펼친다, **Then** 발췌는 표시하지 않고 원문 전체(또는 앞부분)만 보이며 "발췌 없음"이라는 사실이 숨겨지지 않는다.
4. **Given** 발췌가 원문에서 공백·줄바꿈만 다르다, **When** 확인한다, **Then** 같은 문장으로 인정하고 원문의 실제 표기대로 강조한다.
5. **Given** 이 feature 이전에 만들어진 버전이다, **When** 출처를 펼친다, **Then** 발췌 없이 원문이 보이고 오류가 나지 않는다.

### User Story 7 - 로그인, 멤버 관리, 빈 상태·오류 화면이 같은 시각 언어로 정리된다 (Priority: P3)

로그인, 멤버 관리, 그리고 빈 상태(입력 없음, 승인된 입력 없음, 질문만 있고 항목 없음), 오류 상태(갱신 실패, 확정 중 되돌리기 시도, 권한 없음 403, 찾을 수 없음 404)가 시안의 문구와 구조로 정리된다. 멤버 관리는 목록에서 역할을 바꾸면 즉시 저장되고, 마지막 관리자 강등 시도에는 그 행에 오류가 보인다.

**Why this priority**: 사용 빈도가 낮거나 보조적이지만, 일관성과 마감 품질에 필요하다.

**Independent Test**: 각 화면과 상태를 직접 만들어 문구·구조·동작을 시안과 대조한다.

**Acceptance Scenarios**:

1. **Given** 로그인 실패이다, **When** 화면을 본다, **Then** 오류 안내가 폼 위에 아이콘과 글자로 보이고 이메일 입력값은 유지된다. "계정은 보드 관리자가 추가합니다" 안내가 보인다.
2. **Given** 멤버 관리 화면이다, **When** 관리자가 역할을 바꾼다, **Then** 즉시 저장되고, 마지막 관리자를 강등하면 그 행에 이유와 "역할은 관리자로 유지됩니다"가 표시된다. 본인 행에는 "(나)"가 표시된다.
3. **Given** 멤버가 관리자 전용 화면 주소로 접근한다, **When** 화면을 연다, **Then** 403 안내에 현재 내 역할과 "홈으로" 이동이 보인다.
4. **Given** 존재하지 않거나 내가 속하지 않은 보드의 feature 주소이다, **When** 화면을 연다, **Then** 404 안내가 보이고 보드의 존재 여부는 드러나지 않는다.
5. **Given** 승인된 입력이 없거나 입력이 없는 feature이다, **When** 각 탭을 연다, **Then** 다음 행동(첫 입력 제출, 승인 대기 보기)을 안내하는 빈 상태가 보인다.

### User Story 8 - 모든 화면이 일관된 토큰과 접근성 기준을 따르고 라이트·다크 모드를 지원한다 (Priority: P1)

모든 화면은 하나의 색·타이포·간격·모서리 규칙과 공용 컴포넌트(배지, 카드, 출처 패널, 비교 행, 확인 창, 사유 폼, 확정 컨트롤, 버튼)로 만들어진다. 기본은 라이트 모드이고, 사용자의 시스템 설정이 다크이면 시안의 다크 팔레트로 보인다. 상단에는 내 역할 배지가 항상 보이고, 권한 없는 동작은 비활성이 아니라 나타나지 않는다.

**Why this priority**: 다른 모든 스토리의 바탕이며 접근성 기준을 한 번에 보장한다.

**Independent Test**: 모든 화면에 대해 대비, 키보드 조작, 색 비의존 상태 표시, 라이트·다크 전환을 점검한다.

**Acceptance Scenarios**:

1. **Given** 어떤 화면이든, **When** 글자와 배경의 대비를 측정한다, **Then** 라이트와 다크 모두 일반 글자는 4.5:1 이상이다.
2. **Given** 키보드만 사용한다, **When** 모든 화면의 모든 동작(제출, 승인, 반려, 펼치기, 필터, 비교 선택, 되돌리기, 확정)을 수행한다, **Then** 포커스 위치가 보이고 모두 수행할 수 있으며, 확인 창은 포커스를 가두고 Esc로 닫힌다.
3. **Given** 색을 구분하지 못하는 사용자이다, **When** 상태(대기, 승인, 반려, 자동 승인, 열림, 해소, 추가, 삭제, 변경, 확정, 갱신 실패)를 본다, **Then** 모두 아이콘 또는 기호와 글자로 구분된다.
4. **Given** 시스템 설정이 다크이다, **When** 화면을 연다, **Then** 시안의 다크 팔레트로 보이고 라이트와 같은 구조·상태 표시를 가진다.
5. **Given** 역할이 관리자, 멤버, 열람자이다, **When** 상단을 본다, **Then** 내 역할 배지가 보이고, 각 역할에게 허용되지 않는 동작은 화면에 나타나지 않는다.
6. **Given** 좁은 화면(휴대폰 너비)이다, **When** spec 보기와 입력 제출 화면을 연다, **Then** 가로 스크롤 없이 읽고 제출할 수 있고, 미결 질문은 항목 목록 위로 옮겨진다.

---

### Edge Cases

- 번호가 없는 기존 입력과 항목(이 feature 이전 데이터)에는 기존 순서대로 번호가 부여되고, 이후 새 번호와 겹치지 않는다. 번호는 삭제·되돌리기·문구 변경 후에도 재사용되거나 바뀌지 않는다.
- 되돌리기로 만든 버전의 항목은 원래 항목의 번호를 그대로 유지한다.
- "처음 생긴 버전"은 항목이 처음 등장한 버전, "마지막으로 바뀐 버전"은 문구가 직전 버전과 달라진 가장 최근 버전이다. 되돌리기로 이전 문구가 복원되면 그 되돌림 버전이 "마지막으로 바뀐 버전"이 된다.
- 필터 결과가 없으면 빈 상태 문구가 나오고, 필터 선택은 주소에 반영되어 새로고침해도 유지된다.
- 승인 대기 배지 숫자가 매우 커도(예: 100 이상) "99+"처럼 줄여 표시한다.
- 비교할 두 버전의 내용이 같으면 "차이가 없습니다"를 보여준다.
- 되돌리기 영향 미리보기를 연 뒤 다른 변경으로 영향이 달라지면, 확정 직전 최신 기준으로 다시 계산해 달라진 수치를 보여주고 다시 확인을 받는다.
- 발췌가 원문과 완전히 일치하지 않지만 공백·줄바꿈만 다르면 일치로 본다. 그 외 불일치는 발췌를 버린다.
- 한 문장이 원문에 여러 번 나오면 첫 번째 위치를 강조한다.
- 입력 원문이 50,000자에 가까워도 화면이 느려지거나 레이아웃이 깨지지 않는다.
- 사용자가 속한 보드가 여러 개여도 승인 대기 배지와 화면은 현재 보드 기준이다.
- 다크 모드에서도 출처 강조, 비교 강조(추가/삭제/변경), 오류 영역이 구분된다.

## Requirements *(mandatory)*

### Functional Requirements

**디자인 시스템과 접근성**

- **FR-001**: 모든 화면은 하나의 디자인 토큰 집합(색, 글자 크기·굵기·행간, 간격, 모서리)을 사용해야 한다.
- **FR-002**: 공용 컴포넌트(배지, 입력 카드, 항목 카드와 출처 패널, 비교 행, 확인 창, 반려 사유 폼, 확정 컨트롤, 버튼, 빈·오류 상태)는 모든 화면에서 같은 모양과 동작으로 재사용되어야 한다.
- **FR-003**: 기본은 라이트 모드이며, 사용자 시스템 설정이 다크이면 시안의 다크 팔레트로 표시해야 한다. 두 모드 모두 일반 글자 대비가 4.5:1 이상이어야 한다.
- **FR-004**: 모든 상태 표시는 색 외에 아이콘 또는 기호와 글자를 함께 사용해야 한다.
- **FR-005**: 모든 동작은 키보드만으로 수행할 수 있어야 하고, 포커스 위치가 항상 보여야 한다. 확인 창은 열린 동안 포커스를 안에 두고 Esc로 닫혀야 하며, 기본 포커스는 취소에 둔다.
- **FR-006**: 상단에는 로그인한 사용자 이름과 현재 보드 기준 내 역할 배지가 항상 보여야 한다.
- **FR-007**: 사용자 역할이 허용하지 않는 동작·메뉴는 비활성 상태로 두지 않고 화면에 나타나지 않아야 한다. 접근 불가 화면 주소로 직접 들어오면 403 안내가 보여야 한다. 권한 검사는 화면과 관계없이 서버에서도 유지된다(기존 요구사항).
- **FR-008**: 시안의 기본 화면(로그인, 홈, 입력 목록, 승인 대기, 멤버 관리, spec, 버전 이력)은 시안의 구조와 문구를 따라야 한다.
- **FR-009**: spec 보기와 입력 제출 화면은 휴대폰 너비에서도 가로 스크롤 없이 사용할 수 있어야 하며, 이때 미결 질문은 항목 목록 위에 표시한다.

**번호와 변경 표시**

- **FR-010**: 모든 입력은 보드 안에서 유일하고 변하지 않는 읽기 쉬운 번호(IN-n)를 가져야 하며, 입력이 표시되는 모든 곳(입력 목록, 승인 대기, 출처, 버전 근거, 비교)에서 이 번호를 함께 보여야 한다.
- **FR-011**: 모든 spec 항목은 종류별로 유일하고 변하지 않는 번호(결정은 D-n, 요구사항은 R-n)를 가져야 한다. 번호는 문구 변경, 새 버전 생성, 되돌리기 후에도 유지되고 재사용되지 않는다. 미결 질문도 같은 방식의 안정 번호(Q-n)를 가진다.
- **FR-012**: spec 화면의 각 항목에는 "AI 정리"와 함께 항목이 처음 생긴 버전("vN부터")이 표시되어야 하고, 가장 최근 버전에서 새로 생기거나 문구가 바뀐 항목에는 "vN에서 추가"/"vN에서 변경"이 표시되어야 한다.
- **FR-013**: 이 feature 이전에 존재하던 입력과 항목에도 번호가 부여되어야 하며, 기존 데이터의 내용·출처·버전은 변하지 않아야 한다.

**입력 화면**

- **FR-014**: 입력 카드는 번호, 종류, 상태, 제출자, 제출 시각, 원문을 보여주고 원문은 가공 없이 그대로 표시해야 한다. 승인 입력에는 승인자·시각 또는 자동 승인 표시와 "vN에 반영됨/반영 대기"가, 반려 입력에는 사유·반려자·시각과 "spec에 쓰이지 않음"이 표시되어야 한다.
- **FR-015**: 긴 본문은 처음 몇 줄만 보이고 전체 글자 수와 함께 "펼치기"로 전체를 볼 수 있어야 한다.
- **FR-016**: 입력 목록은 필터(전체, 내 대기, 반영 대기, 반려)를 제공하고, 각 필터에 해당 개수를 보여주며, 선택한 필터는 새로고침 후에도 유지되어야 한다. 대기 입력은 관리자와 제출자 본인에게만 보인다는 기존 규칙을 유지하고, 본인 대기 입력에는 그 사실을 안내한다.
- **FR-017**: 입력 제출 폼은 입력 종류 선택, 현재 글자 수와 한도, 제출 후 흐름 안내를 보여야 한다.

**승인 대기**

- **FR-018**: 관리자는 보드 단위의 승인 대기 화면에서 그 보드 모든 feature의 대기 입력을 한 목록으로 보고, 입력마다 어느 프로젝트·feature의 입력인지와 해당 feature로 가는 링크를 볼 수 있어야 한다. 목록은 오래된 순이다.
- **FR-019**: 관리자에게는 상단에 보드의 대기 입력 수가 배지로 항상 보여야 하고(0이면 숫자 숨김, 100 이상은 줄여서 표시), 승인·반려 시 즉시 갱신되어야 한다.
- **FR-020**: 반려는 사유 입력(필수, 제출자에게 그대로 보임 안내)을 거쳐야 하며 취소할 수 있어야 한다. 이미 다른 관리자가 처리한 입력은 안내와 함께 목록에서 갱신되어야 한다.

**홈**

- **FR-021**: 홈은 사용자가 속한 보드별로 프로젝트와 feature를 나열하고, 각 feature에 spec 상태(spec 없음, 최신, 갱신 중, 갱신 실패, 확정됨), 최신 버전 번호와 날짜, 반영 대기 입력 수(0이면 숨김)를 요약해 보여야 한다. 보드 옆에 내 역할을, 관리자 보드에는 승인 대기 링크를 보여야 한다.

**spec 화면**

- **FR-022**: spec 화면은 현재 버전 번호, 생성 시각, 생성 방식, 상태, 이력·비교로 가는 링크를 보여주고, 항목 목록(결정·요구사항 개수 요약 포함), 미결 질문 영역(열림·해소 개수 요약), 최근 버전 목록(최근 3개 정도)을 보여야 한다.
- **FR-023**: 항목의 "출처 N"을 누르면 항목 아래에 출처 입력이 펼쳐지고, 출처마다 입력 번호, 종류, 제출자, 제출 시각, 승인 상태를 보여야 한다. 원문 전체는 한 번 더 눌러서 볼 수 있어야 한다(총 클릭 두 번 이내).
- **FR-024**: 상태별 안내 문구를 제공해야 한다: 갱신 중(읽고 있는 입력 개수를 포함한 진행 안내), 갱신 실패(마지막 성공 버전이 그대로 보인다는 것, 입력이 손실되지 않았다는 것, 시도 횟수와 시각, 관리자에게만 "다시 시도" 동작), 확정(확정자·시각, 해제 시 곧바로 반영될 대기 입력 수), 승인된 입력 없음(대기 중인 입력 수와 승인 대기 보기 링크), 질문만 있고 항목이 없는 경우(단정할 항목이 없음과 질문 보기).
- **FR-025**: 승인되었으나 아직 반영되지 않은 입력이 있으면 spec 화면 상단에 그 개수와 "다음 AI 갱신에 반영됩니다" 안내, 입력 보기 링크를 보여야 한다. 확정 상태에서는 해제 시 반영됨을 안내한다.
- **FR-026**: 해소된 미결 질문은 답과 "답이 된 입력" 출처를 보여주고, 열린 질문에는 관련 입력이 없을 때 그 사실을 보여준다. 열린 질문이 있을 때 "질문에 답하는 입력 제출"로 가는 진입점(멤버·관리자에게만)을 제공한다.

**버전 이력, 비교, 되돌리기**

- **FR-027**: 버전 이력 화면은 버전 카드(번호, 생성 방식, 현재 표시, 시각, 근거 입력 번호, 되돌림 버전은 대상 버전과 실행 관리자)를 최신순으로 보여주고, 사용자는 두 버전을 선택해 A/B로 비교할 수 있어야 한다. 같은 버전을 A와 B로 고를 수 없어야 한다. 버전이 많으면 이전 버전을 더 불러올 수 있어야 한다.
- **FR-028**: 비교 결과는 추가·삭제·변경·동일 개수를 요약하고, 각 변경을 기호·글자·색으로 구분해 보여주며, 변경된 문구는 바뀐 단어를 취소선(이전)과 밑줄(이후)로 강조하고, 새로 붙은 출처를 표시해야 한다. 변경 없는 항목은 기본으로 숨기고 토글로 볼 수 있어야 한다. 두 버전이 같으면 "차이가 없습니다"를 보여준다.
- **FR-029**: 되돌리기는 확인 창을 거치며, 창에는 새 버전이 만들어지고 기존 버전이 남는다는 안내와 영향 미리보기(빠지는 항목 수, 다시 열리는 질문 수)가 보여야 한다. 영향 수치는 실제 되돌린 결과와 같아야 한다.
- **FR-030**: 확인 후 실행 직전에 spec이 확정되었거나 영향이 달라졌으면 되돌리기를 실행하지 않고 최신 상태를 안내해 다시 확인받아야 한다. 확정 상태에서는 되돌리기 버튼 대신 안내와 확정 해제로 가는 링크를 보여준다.

**인용 발췌**

- **FR-031**: AI는 항목(과 질문)의 출처마다 근거가 된 원문 문장(발췌)을 함께 제시해야 한다.
- **FR-032**: 시스템은 제시된 발췌가 해당 입력 원문에 실제로 있는지 확인해야 하며(공백·줄바꿈 차이는 무시), 실제로 있는 발췌만 저장하고 표시해야 한다. 없는 발췌는 버리고 그 출처는 발췌 없이 유지해야 한다. 발췌가 없다는 이유로 항목 생성이 거부되어서는 안 된다.
- **FR-033**: 출처를 펼치면 발췌가 있는 출처는 원문 중 그 문장을 강조해 보여주고 "원문 전체 보기"를 제공하며, 발췌가 없는 출처는 원문만 보여주어야 한다. 이 feature 이전에 만들어진 버전은 발췌 없이 오류 없이 표시되어야 한다.

**멤버 관리, 로그인, 상태 화면**

- **FR-034**: 멤버 관리 화면은 이름, 이메일, 역할, 추가일을 표로 보여주고, 본인 행에 "(나)"를 표시하며, 역할 변경은 즉시 저장되어야 한다. 마지막 관리자 강등 시도에는 그 행에 이유와 역할 유지 안내를 보여준다.
- **FR-035**: 로그인 화면은 실패 안내를 폼 위에 보여주고 이메일 입력값을 유지하며, 계정은 보드 관리자가 추가한다는 안내를 보여야 한다.
- **FR-036**: 403, 404, 빈 상태(입력 없음, 승인된 입력 없음, 필터 결과 없음)는 다음 행동을 안내하는 화면으로 제공해야 한다. 404는 접근 권한이 없는 보드의 존재 여부를 드러내서는 안 된다.

### Key Entities *(include if feature involves data)*

- **입력(Input)**: 001·002에서 정의된 입력. 이 feature에서 보드 안에서 유일한 읽기 쉬운 번호(IN-n)를 추가로 가진다.
- **Spec 항목(SpecItem)**: 002에서 정의된 항목. 종류별 안정 번호(D-n/R-n)와 이 항목이 처음 생긴 버전, 마지막으로 바뀐 버전을 알 수 있어야 한다.
- **출처 연결(항목·질문과 입력의 연결)**: 002에서 정의된 연결. 이 feature에서 연결마다 선택적인 인용 발췌(원문 중 실제로 존재하는 문장)를 가질 수 있다.
- **보드 요약**: 홈과 승인 대기 배지를 위한 보드 단위 집계(대기 입력 수, feature별 spec 상태·최신 버전·날짜·반영 대기 입력 수). 저장 데이터가 아니라 기존 데이터의 조회 결과다.
- **되돌리기 영향**: 특정 버전으로 되돌릴 때 사라지는 항목 수와 다시 열리는 질문 수. 저장되지 않는 계산 결과다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 모든 화면에서 일반 글자의 대비가 라이트·다크 두 모드 모두 4.5:1 이상이다(자동 점검 위반 0건).
- **SC-002**: 모든 화면의 모든 동작이 키보드만으로 수행되고, 확인 창은 Esc로 닫히며 포커스가 창 밖으로 나가지 않는다(점검 항목 100% 통과).
- **SC-003**: 시안에 나오는 모든 상태 표시의 100%가 색 외에 아이콘·기호와 글자로도 구분된다.
- **SC-004**: 팀원이 spec 항목의 근거 입력을 확인하는 데 클릭 두 번 이내이고, 발췌가 있는 항목은 강조된 문장을 첫 번째 클릭에서 바로 볼 수 있다.
- **SC-005**: 표시되는 인용 발췌의 100%가 원문에 실제로 존재하는 문장이다(원문에 없는 발췌 표시 0건).
- **SC-006**: 관리자가 여러 feature에 걸친 대기 입력 10개를 feature 화면으로 이동하지 않고 승인 대기 한 화면에서 처리할 수 있다.
- **SC-007**: 되돌리기 확인 창의 영향 수치(빠지는 항목 수, 다시 열리는 질문 수)가 실제 되돌린 결과와 100% 일치한다.
- **SC-008**: 권한이 허용하지 않는 동작·메뉴가 화면에 나타나는 경우가 0건이고, 직접 주소 접근은 100% 403 또는 404 안내로 처리된다.
- **SC-009**: 모든 입력과 모든 spec 항목에 번호가 있고, 번호가 중복되거나 바뀌거나 재사용되는 경우가 0건이다. 이 feature 적용 전 데이터도 내용 손실 없이 번호가 부여된다.
- **SC-010**: 휴대폰 너비에서 spec 보기와 입력 제출 화면이 가로 스크롤 없이 사용 가능하다.
- **SC-011**: 시안의 화면 구성 요소 점검표(화면별 필수 요소 목록)에 대해 구현이 누락 없이 일치한다는 검토 확인을 받는다.

## Assumptions

- 시안 PDF(`docs/Specboard-selection.pdf`)가 화면 구조·문구·시각 규칙의 기준이고, 시안과 이 문서가 다르면 이 문서의 범위와 기능 규칙이 우선한다. 시안에 있지만 범위 밖으로 명시한 요소(회의 제목, 질문 연결 힌트, 충돌 경고 "예정" 표시)는 만들지 않는다.
- 입력 번호는 보드 단위로 1부터 순서대로 부여된다(시안에서 한 보드의 여러 feature가 IN-7, IN-31처럼 같은 번호 체계를 쓰는 것에 따름). 항목 번호는 feature의 spec 안에서 종류별로 1부터 부여된다.
- 기존 데이터의 번호는 제출 시각 순으로 부여한다.
- 다크 모드는 사용자의 시스템 설정을 따르며 수동 전환 스위치는 이번 범위에 없다.
- 글꼴은 시안이 제안한 본문 UI용과 숫자·ID용 두 종류를 사용하되, 해당 글꼴을 불러오지 못하면 시스템 글꼴로 대체되어도 레이아웃이 깨지지 않는다.
- "AI 정리"와 "원문" 구분은 spec 항목은 AI가 정리한 것, 입력은 사람이 쓴 원문 그대로라는 뜻의 표시이며, 새로운 사람 편집 기능을 뜻하지 않는다.
- 인용 발췌는 AI 갱신이 새로 만드는 버전부터 채워진다. 이미 존재하는 버전에는 소급 생성하지 않는다.
- 승인 대기 화면은 현재 보드 기준이며, 사용자가 속한 여러 보드를 가로지르는 통합 승인 대기는 범위 밖이다.
- 홈의 반영 대기 입력 수는 "승인되었으나 어떤 버전에도 반영되지 않은 입력" 수다.
- 되돌리기 영향 미리보기의 "다시 열리는 질문"은 현재 해소 상태인데 대상 버전에서는 열림이거나 존재하지 않는 질문 수이고, "빠지는 항목"은 현재 있으나 대상 버전에 없는 항목 수다.
- 알림, 가입, 멤버 제거, 충돌 경고, 마크다운 내보내기는 이번 범위 밖이다.
