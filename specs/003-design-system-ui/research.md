# Research: 디자인 시안 적용

시안 PDF에서 읽은 값(색, 글꼴, 간격)은 **토큰의 출발점**이며, 구현은 CSS 변수로 옮기고 대비 점검(axe)으로 검증한다.

| 결정 | 선택 | 근거 | 검토한 대안 |
|---|---|---|---|
| 스타일 방식 | 일반 CSS + CSS 변수(`tokens.css`, `base.css`, `components.css`), 다크는 `@media (prefers-color-scheme: dark)`로 같은 변수 이름만 덮어씀 | 시안이 "CSS 변수 그대로 Next.js 전역 CSS에 옮길 수 있다"고 명시. 지정된 스택 유지. 서버 컴포넌트와 충돌 없음 | Tailwind·CSS-in-JS: 새 의존성. 이번 범위에서 이득이 크지 않음 |
| 토큰 값 | 라이트 `bg #F5F6F8, surface #FFFFFF, ink #15171C, ink-3 #5C6371, src #1D5BD0, q #9A4700, ai #5B3FC4, line #DCE0E6, ok #16683B, wait #6E5600, no #B3261E, auto #0D5F6E`. 다크 `bg #111317, surface #1A1D23, ink #ECEEF2, ink-3 #9EA5B2, src #8DB4FF, q #FFB46B, ai #C2B2FF, line #2E333C, ok #7FD6A1, wait #F2D36B, no #FF9A92, auto #7FD3E0`. 간격 4·8·12·16·24·32·48, 모서리 배지 6·버튼 8·카드 12·출처 칩 full, 타이포 display 28/1.3·700, h2 18/1.4·600, item 16/1.65, body 15/1.7, small 13/1.6, meta mono 12 | 시안 3쪽의 토큰 표 | 임의 값: 시안과 어긋남 |
| 색 의미 | `--src`(파랑)=출처·링크, `--q`(주황)=미결 질문, `--ai`(보라)=AI 정리, `--ok/--wait/--no/--auto`=입력 상태. 의미 외의 용도로 쓰지 않음 | 시안의 "신뢰를 만드는 세 가지 표시"(출처, 미결 질문, AI vs 원문) | 색을 장식으로 사용: 의미 혼선 |
| 글꼴 | `next/font/google`의 IBM Plex Sans KR(본문)과 IBM Plex Mono(번호·시각·ID), 시스템 글꼴 대체 스택과 `display: swap`. 줄바꿈은 `word-break: keep-all` | 시안 지정. `next/font`는 Next 내장(새 라이브러리 아님), 빌드 시 자체 호스팅 | 외부 CDN 링크: 외부 의존·개인정보. 시스템 글꼴만: 시안과 다름 |
| 아이콘 | 인라인 SVG 컴포넌트 약 15개(`Icon`) | 아이콘 라이브러리 없이 시안 수준 충족. 색과 무관한 의미 전달(접근성) | 아이콘 패키지: 새 의존성 |
| 확인 창 | 네이티브 `<dialog>` + `showModal()` | 포커스 가둠, Esc 닫기, 배경 비활성이 브라우저 기본. 기본 포커스는 취소 버튼에 `autofocus` | 직접 만든 모달: 접근성 구현 부담 |
| 다크 모드 | 시스템 설정 자동 적용, 수동 스위치 없음 (spec Assumptions) | 범위 최소화, 시안은 "제안" 수준 | 수동 토글: 상태 저장 필요 |
| 접근 불가 화면(403) | 페이지가 권한을 확인해 403 안내 화면을 렌더링(HTTP는 200). JSON API는 403 상태 유지 | Next의 `forbidden()`은 실험 기능. 서버 검사는 서비스에서 그대로 수행되어 보안에는 영향 없음 | 실험 플래그 사용: 안정성 위험 |
| 입력 번호 | 보드 단위 카운터(`Board.inputSeq`)를 제출 트랜잭션 안에서 `UPDATE ... SET inputSeq = inputSeq + 1 RETURNING`으로 원자적으로 증가, `Input.number`와 `(boardId, number)` 유니크 | 동시 제출에도 중복·결번 없이 단조 증가(결번은 롤백 시 허용하지 않도록 같은 트랜잭션) | `MAX()+1`: 경쟁 조건. 시퀀스: 보드별 시퀀스 관리 복잡 |
| 항목 번호 | `Spec.decisionSeq`, `Spec.requirementSeq` 카운터. 새 항목 key가 처음 저장될 때(feature 락 안) 번호 부여, 같은 key의 모든 버전 행에 같은 번호 복사. 기존 key의 `kind` 변경은 출력 검증에서 거부 | D-1이 R-1로 바뀌는 혼선 방지. 되돌리기는 행을 복사하므로 번호 유지 | 매 버전 재번호: "안정 번호" 위배 |
| 기존 데이터 번호 | 마이그레이션 SQL에서 `row_number() OVER (PARTITION BY board ORDER BY submittedAt, id)`로 입력 번호, key별 최초 등장 순서로 항목 번호를 채우고 카운터를 최댓값으로 설정 | 내용 손실 없이 일괄 부여(FR-013). 개발 DB에 실제 누적 데이터가 있어 검증 가능 | 앱 기동 시 스크립트: 실패·중복 실행 위험 |
| 변경 버전 표시 | 저장하지 않고 조회 시 계산: spec의 전 버전 항목을 `(key, text, versionNumber)`로 한 번에 읽어 key별 "처음 등장 버전"과 "직전 존재 버전과 문구가 달라진 가장 최근 버전"을 구함(되돌리기로 복원된 문구도 그 되돌림 버전을 변경으로 봄) | 저장 컬럼은 되돌리기·삭제와 어긋날 위험. 규모(버전 수십~수백 × 항목 수십)에서 계산 비용이 작음 | 컬럼 저장: 불변 스냅샷과 동기화 부담 |
| 인용 발췌 저장 | 출처 연결마다 `quoteStart`, `quoteEnd`(원문 문자 오프셋, nullable). 문장 자체는 저장하지 않고 원문 슬라이스로 표시 | 입력 원문은 불변이라 오프셋이 안정적이고, 발췌가 원문과 어긋날 수 없음. 중복 저장 없음 | 문장 텍스트 저장: 원문과 불일치 가능 |
| 발췌 검증 | AI는 출처마다 `quotes: [{inputId, quote}]`를 선택적으로 제시. 서버는 공백·줄바꿈을 `\s+`로 정규화해 원문에서 첫 일치를 찾고(원문 실제 표기의 범위를 계산), 길이 500자 이하·1자 이상만 인정. 불일치·과다 길이는 버리고 발췌 없는 출처로 저장. 기존 항목의 이미 저장된 발췌는 같은 출처를 다시 인용하지 않으면 유지 | 지어낸 인용 0건(SC-005). 발췌 문제로 항목 생성이 막히지 않음(FR-032) | 불일치 시 출력 거부: 가용성 저하. 퍼지 매칭: 오탐 위험 |
| AI 출력 변경 | 기존 `sourceInputIds`는 유지하고 `quotes` 배열(빈 배열 허용)을 추가. 프롬프트에 "quote는 원문에서 그대로 복사한 한 문장, 확실하지 않으면 생략" 지시 | 002의 검증·테스트 변경 최소화. 구조화 출력 스키마만 확장 | 출처를 객체 배열로 교체: 002 코드·테스트 전면 수정 |
| 보드 승인 대기 | `board-pending` 서비스: `Input.boardId`(비정규화 컬럼, 번호 유니크에도 사용)로 보드 전체 PENDING을 한 쿼리로 조회, feature·프로젝트 이름을 join, 정렬은 제출 시각 오름차순. 개수 API 별도 | 상단 배지를 모든 화면에서 싼 쿼리로 | feature별 합산: N+1 |
| 홈 요약 | `home` 서비스가 사용자의 보드·프로젝트·feature를 가져오고 spec, 최신 버전, 활성·실패 작업, 반영 대기 수를 `groupBy`/`IN` 쿼리로 한 번씩만 조회해 메모리에서 조합. 상태 판정은 `deriveSpecStatus` 공용 함수 | N+1 방지, getSpec과 상태 규칙 일치 | feature마다 getSpec 호출: 쿼리 폭증 |
| 입력 필터 | `all`, `mine-pending`(내가 낸 PENDING), `reflect-pending`(APPROVED이고 미반영), `rejected`. 필터와 개수 모두 001의 가시성 규칙(비관리자는 타인의 대기 입력 불가) 안에서 계산. 선택은 쿼리스트링 `?filter=` | 시안의 필터 칩. 새로고침 유지(FR-016) | 클라이언트 필터링: 개수·가시성 규칙 중복 |
| 입력 목록 페이징 | `limit`(기본 20, 최대 100) + `cursor`(마지막 입력 id), 응답에 `nextCursor` | "이전 입력 N개 더 보기" | 전체 로드: 수천 건에서 느림 |
| 되돌리기 미리보기 | `revert-preview` 서비스가 최신과 대상 버전의 항목·질문 key를 비교해 `removedItems`(최신에 있고 대상에 없는 항목), `reopenedQuestions`(최신에서 RESOLVED인데 대상에서 OPEN이거나 없는 질문)과 라벨 목록을 계산. `revertSpec`은 같은 함수를 호출하고, 요청에 `expected`(최신 버전 번호와 수치)가 있으면 불일치 시 409 `PREVIEW_CHANGED`와 최신 미리보기를 돌려줌 | 미리보기와 실제 결과의 일치(SC-007)와 확정·변경 레이스 처리(FR-030) | 클라이언트 계산: 규칙 중복 |
| 비교 확장 | diff 서비스에 항목 라벨·종류, `unchanged` 개수, 항목별 `addedSources`(to에만 있는 출처의 IN 번호)를 추가. 단어 단위 강조는 `lib/word-diff.ts`(토큰 LCS, 공백·한글 어절 기준)를 화면과 단위 테스트가 공용으로 사용 | 시안의 "추가 2 · 삭제 1 · 변경 2 · 동일 3", 이전/이후 단어 강조, "새 출처" | 외부 diff 라이브러리: 새 의존성 |
| A/B 선택 | 이력 화면 클라이언트 컴포넌트가 체크 상태를 관리하고 `?a=&b=`를 주소에 반영. 같은 버전을 둘 다 고르면 거부 | 새로고침·공유 가능. JS 없는 환경에서는 select 폼으로 대체 | 서버 폼만: 체크박스 UX 불가 |
| 헤더·탭 | `boards/[boardId]/layout.tsx`가 내 역할과 관리자일 때 대기 수를 가져와 `AppHeader`에 전달. feature 레이아웃의 탭(Spec / 입력 N / 버전 이력)이 기존 URL을 그대로 사용 | URL 호환 유지, 모든 보드 화면에서 배지 갱신 | 각 페이지가 개별 조회: 중복 |
| 기존 per-feature 승인 대기 | `/features/[f]/inputs/pending`는 `/boards/[b]/pending?feature=[f]`로 리다이렉트하고, API는 유지 | 001 링크·북마크 호환 | 삭제: 링크 깨짐 |
| 반응형 | spec 보기와 입력 제출 화면에 `@media (max-width: 720px)`: 단일 컬럼, 미결 질문을 항목 위로 이동(CSS order), 제출 폼을 목록 위로 | FR-009. 나머지 화면은 데스크톱 우선 | 전 화면 반응형: 범위 초과 |
| 접근성 검증 | Playwright + `@axe-core/playwright`로 모든 화면을 라이트·다크(`emulateMedia`)로 점검(color-contrast 포함), 키보드 시나리오 테스트(Tab/Enter/Esc), 포커스 가둠 확인 | SC-001~003을 자동으로 회귀 방지 | 수동 점검만: 회귀 취약 |
| 모바일 앱 대비 | 새 데이터는 모두 서비스로 구현하고 JSON API로 노출. 인증은 지금 쿠키 세션이며 네이티브 앱용 토큰 인증은 앱 착수 시 별도 feature | 지정된 설계 원칙 | 지금 토큰 인증: 범위 밖 |

미해결 NEEDS CLARIFICATION: 없음. 측정·검증 후 조정할 값: 발췌 최대 길이(500자), 입력 목록 기본 페이지 크기(20).
