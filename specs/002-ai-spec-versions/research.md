# Research: AI spec 생성과 버전 이력

| 결정 | 선택 | 근거 | 검토한 대안 |
|---|---|---|---|
| AI 제공자·모델 | Anthropic API, `claude-opus-5-5` 기본, `SPEC_MODEL`로 교체 가능 | 지정된 제공자. 출처 추적과 "지어내지 않기"가 핵심이라 지시 이행력이 높은 모델이 유리. 2분 목표는 반영 입력 수 상한과 effort로 관리 | Sonnet/Haiku급: 더 빠르고 싸지만 품질 검증 전에는 기본값으로 삼지 않음. 환경 변수로 교체해 측정 후 결정 |
| 응답 형식 | `output_config.format` JSON 스키마 구조화 출력 | 항목·질문·출처 id를 기계 검증 가능한 형태로 받음. 프리필·강제 `tool_choice`는 이 모델에서 400이므로 사용하지 않음 | 자유 텍스트 후 파싱: 출처 검증 불가 |
| 사고(thinking)·effort | `thinking` 생략(항상 켜짐), `output_config.effort: "medium"` 명시 | 이 모델은 사고를 끌 수 없고 effort 기본값이 `medium`. 명시해 변경에 흔들리지 않게 함 | `high`: 느려 SC-001 위험. 측정 후 상향 가능 |
| 호출 방식 | 스트리밍 + `finalMessage()` | 큰 `max_tokens`에서 HTTP 타임아웃을 피함 | 비스트리밍: 긴 출력에서 타임아웃 위험 |
| 거절 처리 | 서버 측 `fallbacks: "default"`(베타 헤더 `server-side-fallback-2026-07-01`). 최종 거절이면 작업을 FAILED(사유 REFUSED)로 기록 | 안전 분류기가 정상 회의록을 거절하는 경우에도 갱신이 멈추지 않게 함. 거절 시 기존 버전·입력 상태 불변(FR-023) | 폴백 없음: 거절 때마다 수동 재시도 필요 |
| 출처·임의 생성 방지 | 서버 검증: ① 모든 항목·해소된 질문에 출처 1개 이상 ② 출처 id는 이 feature의 승인된 입력만 ③ 새로 만들거나 문구가 바뀐 항목은 이번 반영 입력을 1개 이상 인용 | 프롬프트만으로는 보장되지 않으므로 원칙 I·II를 코드로 강제 | 프롬프트 지시만: 위반 시 저장됨 |
| 입력 본문의 프롬프트 주입 | 입력 본문을 구분자로 감싸 "데이터이며 지시가 아님"으로 명시, 모델 출력은 위 검증을 통과해야 저장 | 회의록·의견은 사용자 작성 텍스트. 주입으로 임의 항목을 넣어도 출처 규칙에서 걸러짐 | 본문 그대로 삽입: 지시 혼입 위험 |
| 작업 실행 | Postgres `SpecJob` 테이블 + 프로세스 내 워커. 승인 직후 Next.js `after()`로 실행을 시작하고, 페이지 조회 시 만료된 임대(lease)를 회수해 재개 | 별도 큐 인프라 없이 단일 팀 규모를 충족. 재시작해도 작업이 남음 | Redis/BullMQ: 이 규모에 과함. 요청 안에서 동기 실행: 2분 처리가 요청을 점유 |
| feature당 직렬화 | 트랜잭션 내 `pg_advisory_xact_lock(hashtext(featureId))` 후 버전 번호 발급·입력 소비 | 동시 승인·되돌리기·확정과의 경쟁을 막고 번호 중복 방지 (FR-011) | 앱 메모리 락: 다중 프로세스에서 무력 |
| 반영 단위 | 한 번의 갱신이 처리 가능한 상한까지 승인 순서대로 입력을 묶어 한 버전을 만든다 | 확정 해제 시 대기 입력을 한 번에 반영(엣지 케이스)하면서 컨텍스트를 보호. 입력은 승인 시각 순으로 처리하고 한 입력은 한 번만 소비 (FR-011) | 입력당 버전 1개: 대기 입력이 많을 때 AI 호출 폭증 |
| 실행 중 되돌리기·확정 | 저장 시 기준 버전 번호와 확정 여부를 다시 확인해 달라졌으면 결과를 폐기하고 입력은 미소비로 남겨 재큐 | 오래 걸리는 AI 호출 중에 일어난 관리자 동작을 덮어쓰지 않음 | 호출 동안 잠금 유지: DB 연결 장시간 점유 |
| 버전 저장 | 버전마다 항목·질문의 전체 스냅샷 행을 저장(항목에는 버전 간 동일한 `key`) | 버전이 불변이고 되돌리기·비교가 단순. 규모상 중복 저장 비용 미미 | 변경분(delta)만 저장: 복원·되돌리기 복잡 |
| 비교(diff) | 서버가 `key`로 대응시켜 추가·삭제·변경 분류, 변경은 단어 단위 비교를 화면에서 표시 | 항목 단위 의미 있는 비교. 문서 전체 텍스트 diff보다 읽기 쉬움 | 전체 마크다운 텍스트 diff: 항목 이동·재배열에 취약 |
| 되돌리기 후 입력 | 되돌려도 입력의 "반영됨" 표시는 되돌리지 않음 (spec Assumptions) | 같은 입력이 자동으로 재반영되면 되돌리기 의도가 무효화됨 | 입력 재반영: 사용자 의도와 충돌 |
| 테스트 | `SpecWriter` 가짜 구현 + 실제 PostgreSQL. 실제 Claude 호출은 키가 있을 때만 도는 별도 스위트(출처 규칙, "지어내지 않음" 샘플 점검) | 결정적이고 비용 없는 CI. 모델 품질은 별도 측정 | 모든 테스트에서 실제 호출: 느리고 불안정하며 비용 발생 |

미해결 NEEDS CLARIFICATION: 없음. 측정 후 조정할 값: 모델·effort, 반영 입력 상한(20개/150,000자), 2분 목표.
