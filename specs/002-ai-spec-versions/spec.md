# Feature Specification: AI spec 생성과 버전 이력

**Feature Branch**: `002-ai-spec-versions`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "AI spec 생성과 버전 이력 feature. feature마다 하나의 spec 문서가 있고, 승인된 입력(회의록, 아이디어, 의견)만 재료로 AI가 spec을 작성·갱신한다. 입력이 승인되면 AI가 사람의 추가 승인 없이 spec의 새 버전을 자동으로 만든다. spec의 각 결정·요구사항은 근거가 된 입력과 연결되어 출처를 확인할 수 있어야 하고, 출처 없는 내용은 넣지 않는다. 입력이 빈약하거나 정보가 부족하면 AI는 내용을 지어내지 않고 \"미결 질문\"으로 남긴다. spec 변경은 덮어쓰지 않고 새 버전으로 쌓이며, 각 버전은 어떤 입력에서 나온 변경인지 기록하고 이전 버전과 비교하거나 되돌릴 수 있다. 되돌리면 이전 내용이 새 버전으로 만들어진다. 모든 멤버 역할은 spec과 이력을 열람할 수 있고, 되돌리기와 spec 확정은 관리자만 한다. 확정된 spec은 이후 입력이 승인되어도 자동으로 바뀌지 않고, 관리자가 확정을 해제해야 갱신이 재개된다. 이전 feature(001-input-approval)의 승인된 입력 조회를 재료로 사용한다. 새 입력과 확정된 결정의 충돌 경고, spec 마크다운 내보내기, 실시간 공동 편집은 이 feature 범위가 아니다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 승인된 입력으로 spec이 자동으로 만들어지고 갱신된다 (Priority: P1)

관리자가 입력을 승인하면(또는 관리자가 직접 낸 입력이 자동 승인되면) AI가 그 입력을 재료로 해당 feature의 spec을 작성하거나 갱신한다. 사람의 추가 승인 없이 새 버전이 만들어지고, 팀원은 최신 spec을 열람한다.

**Why this priority**: 회의 내용이 기록 기반 문서로 이어지는 것이 이 제품의 핵심 가치다. 이것만 있어도 승인된 논의가 spec으로 정리된다.

**Independent Test**: 입력을 승인한 뒤 해당 feature에 새 spec 버전이 생기고 승인된 입력의 내용이 반영되었는지 확인한다.

**Acceptance Scenarios**:

1. **Given** spec이 아직 없는 feature에서 입력이 승인된다, **When** AI 처리가 끝난다, **Then** 첫 번째 spec 버전이 만들어지고 승인된 입력의 내용이 담긴다.
2. **Given** spec이 이미 있는 feature에서 새 입력이 승인된다, **When** AI 처리가 끝난다, **Then** 기존 버전은 그대로 남고 새 입력이 반영된 새 버전이 추가된다.
3. **Given** 대기 또는 반려 상태의 입력이 있다, **When** AI가 spec을 만든다, **Then** 그 입력의 내용은 어떤 버전에도 반영되지 않는다.
4. **Given** 여러 입력이 거의 동시에 승인된다, **When** AI 처리가 모두 끝난다, **Then** 모든 입력이 빠짐없이 반영되고 버전은 승인 순서대로 쌓인다.

---

### User Story 2 - spec의 모든 내용은 출처를 가지고, 부족한 정보는 미결 질문으로 남는다 (Priority: P1)

spec의 각 결정과 요구사항에는 근거가 된 입력이 연결되어, 팀원이 "이 내용이 어느 회의, 누구의 의견에서 나왔는지" 확인할 수 있다. 입력이 빈약하거나 정보가 부족하면 AI는 내용을 지어내지 않고 "미결 질문"으로 남긴다. 이후 새 입력이 질문에 답하면 질문이 해소된다.

**Why this priority**: 출처 추적과 임의 생성 금지는 이 제품이 신뢰를 얻는 조건이며, 팀 결정 충돌을 막는 근거 기록이 된다.

**Independent Test**: 한 줄짜리 아이디어를 승인해 spec이 만들어졌을 때 모든 항목에 출처가 있고, 입력에 없는 내용이 미결 질문으로 분리되어 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** spec의 한 항목이 있다, **When** 팀원이 그 항목의 출처를 연다, **Then** 근거가 된 입력(종류, 제출자, 제출 시각, 내용)을 확인할 수 있다.
2. **Given** 승인된 입력이 "알림이 있으면 좋겠다" 한 줄뿐이다, **When** AI가 spec을 만든다, **Then** 알림 방식, 대상, 시점 등 입력에 없는 세부 내용은 지어내지 않고 미결 질문으로 남는다.
3. **Given** 미결 질문이 있다, **When** 그 질문에 답하는 입력이 승인된다, **Then** 질문은 해소 상태가 되고 답이 spec 항목으로 반영되며 출처가 연결된다.
4. **Given** 어떤 내용이 어느 승인된 입력에서도 도출되지 않는다, **When** AI가 spec을 만든다, **Then** 그 내용은 spec에 포함되지 않는다.

---

### User Story 3 - 버전 이력을 보고 이전 버전과 비교한다 (Priority: P2)

팀원은 spec의 버전 목록을 보고, 각 버전이 언제 어떤 입력으로 만들어졌는지 확인하며, 두 버전을 비교해 무엇이 바뀌었는지 볼 수 있다.

**Why this priority**: 변경의 이유를 되짚을 수 있어야 팀이 spec을 신뢰한다. 생성(P1) 이후에 필요하다.

**Independent Test**: 입력 두 개를 차례로 승인해 버전 두 개를 만든 뒤, 이력 목록과 두 버전의 차이를 확인한다.

**Acceptance Scenarios**:

1. **Given** spec에 버전이 여러 개 있다, **When** 팀원이 이력을 연다, **Then** 버전 번호, 생성 시각, 변경 근거가 된 입력 목록이 최신순으로 보인다.
2. **Given** 두 버전을 선택한다, **When** 비교를 연다, **Then** 추가·삭제·변경된 내용이 구분되어 보인다.
3. **Given** 어떤 멤버 역할이든(관리자, 멤버, 열람자), **When** spec과 이력을 연다, **Then** 열람할 수 있다.
4. **Given** 보드에 속하지 않은 사용자이다, **When** spec을 열람하려 한다, **Then** 거부된다.

---

### User Story 4 - 관리자가 이전 버전으로 되돌린다 (Priority: P2)

AI가 잘못 반영했거나 방향이 틀어졌을 때 관리자가 이전 버전으로 되돌린다. 되돌리기는 이력을 지우지 않고, 선택한 이전 버전의 내용을 담은 새 버전을 만든다.

**Why this priority**: 사람의 승인 없이 AI가 갱신하는 구조의 안전장치다.

**Independent Test**: 버전 3개가 있는 spec을 버전 1로 되돌리고, 버전 4가 새로 생겼으며 그 내용이 버전 1과 같고 기존 버전 1~3이 그대로인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 버전이 여러 개 있다, **When** 관리자가 이전 버전을 골라 되돌린다, **Then** 그 버전과 같은 내용의 새 버전이 최신으로 생기고 기존 버전은 모두 보존된다.
2. **Given** 되돌리기로 만들어진 버전이다, **When** 이력을 본다, **Then** "버전 N으로 되돌림"으로 표시되고 실행한 관리자가 기록된다.
3. **Given** 멤버 또는 열람자이다, **When** 되돌리기를 시도한다, **Then** 거부된다.
4. **Given** 최신 버전과 같은 내용의 버전을 고른다, **When** 되돌리기를 시도한다, **Then** 변화가 없다고 알리고 새 버전을 만들지 않는다.

---

### User Story 5 - 관리자가 spec을 확정하고 해제한다 (Priority: P2)

관리자가 spec을 확정하면 이후 입력이 승인되어도 spec이 자동으로 바뀌지 않는다. 새로 승인된 입력은 "반영 대기"로 쌓이고, 관리자가 확정을 해제하면 갱신이 재개되어 쌓인 입력이 반영된다.

**Why this priority**: 합의된 spec을 보호해 구현 중 의도치 않은 변경을 막는다.

**Independent Test**: spec을 확정한 뒤 새 입력을 승인해도 새 버전이 생기지 않고, 확정을 해제하면 반영되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** spec이 있다, **When** 관리자가 확정한다, **Then** spec은 "확정" 상태가 되고 확정한 관리자와 시각이 기록된다.
2. **Given** 확정된 spec이다, **When** 새 입력이 승인된다, **Then** 새 버전은 만들어지지 않고 그 입력은 "반영 대기"로 표시된다.
3. **Given** 반영 대기 입력이 있는 확정 spec이다, **When** 관리자가 확정을 해제한다, **Then** 대기 중이던 입력이 반영되어 새 버전이 만들어진다.
4. **Given** 멤버 또는 열람자이다, **When** 확정이나 해제를 시도한다, **Then** 거부된다.
5. **Given** 확정된 spec이다, **When** 관리자가 되돌리기를 시도한다, **Then** 확정을 먼저 해제하라는 안내와 함께 거부된다.

---

### Edge Cases

- AI 처리가 실패하면 기존 spec과 모든 버전은 그대로 유지되고, 입력은 승인 상태를 잃지 않으며, 반영은 나중에 다시 시도된다. 사용자에게 실패 상태가 보인다.
- 승인된 입력이 하나도 없는 feature에는 빈 spec 대신 "승인된 입력이 아직 없습니다" 안내가 표시된다.
- 같은 입력이 두 번 반영되지 않는다. 입력은 한 번의 갱신에서만 사용된다.
- 되돌리기 이전에 반영되었던 입력은 되돌린 뒤 자동으로 다시 반영되지 않는다. 이후 승인되는 새 입력만 반영된다.
- 미결 질문에 대한 답이 새 입력에 없으면 질문은 열린 상태로 남는다.
- 새 입력이 기존 항목과 모순돼 보여도 이 feature에서는 경고하지 않고 최신 입력 기준으로 반영하며, 이전 버전은 보존된다(충돌 경고는 별도 feature).
- 매우 긴 회의록이 승인되어도 처리되어야 하며, 처리 중에는 처리 중 상태가 표시된다.
- 확정된 spec에서 쌓인 반영 대기 입력이 많아도 해제 시 한 번의 갱신으로 모두 반영될 수 있어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 feature마다 하나의 spec 문서를 가져야 한다.
- **FR-002**: 입력이 승인되면(관리자 자동 승인 포함) 시스템은 그 입력을 재료로 spec의 새 버전을 사람의 추가 승인 없이 자동으로 만들어야 한다.
- **FR-003**: spec 작성·갱신에는 승인 상태의 입력만 사용해야 한다. 대기와 반려 입력은 사용해서는 안 된다.
- **FR-004**: spec의 각 결정과 요구사항 항목은 근거가 된 하나 이상의 입력과 연결되어야 한다.
- **FR-005**: 사용자는 spec 항목에서 근거 입력의 종류, 제출자, 제출 시각, 내용을 확인할 수 있어야 한다.
- **FR-006**: 승인된 입력에서 도출되지 않는 내용은 spec에 포함되어서는 안 된다.
- **FR-007**: 입력의 정보가 부족한 사항은 지어내지 않고 "미결 질문"으로 spec에 기록해야 한다.
- **FR-008**: 미결 질문은 열림과 해소 상태를 가지며, 답을 담은 입력이 승인되면 해소 상태가 되고 답이 spec 항목으로 반영되어야 한다.
- **FR-009**: spec 변경은 기존 내용을 덮어쓰지 않고 항상 새 버전으로 쌓여야 한다.
- **FR-010**: 각 버전은 번호, 생성 시각, 변경 근거가 된 입력 목록, 생성 방식(AI 갱신, 되돌리기)을 기록해야 한다.
- **FR-011**: 한 입력은 한 번의 갱신에서만 반영되어야 하며, 여러 입력이 동시에 승인되어도 모두 빠짐없이 승인 순서대로 반영되어야 한다.
- **FR-012**: 사용자는 spec의 버전 목록과 각 버전의 내용을 볼 수 있어야 한다.
- **FR-013**: 사용자는 두 버전을 선택해 추가·삭제·변경된 내용을 비교할 수 있어야 한다.
- **FR-014**: 관리자는 이전 버전으로 되돌릴 수 있어야 하며, 되돌리기는 선택한 버전과 같은 내용의 새 버전을 만들고 기존 버전을 모두 보존해야 한다.
- **FR-015**: 되돌리기로 만들어진 버전은 어느 버전으로 되돌렸는지와 실행한 관리자를 기록해야 한다.
- **FR-016**: 최신 버전과 내용이 같은 버전으로의 되돌리기는 새 버전을 만들지 않고 안내해야 한다.
- **FR-017**: 관리자는 spec을 확정하고 해제할 수 있어야 하며, 확정과 해제의 수행자와 시각이 기록되어야 한다.
- **FR-018**: 확정된 spec은 입력이 승인되어도 새 버전을 만들지 않아야 하며, 그 입력은 "반영 대기"로 표시되어야 한다.
- **FR-019**: 확정이 해제되면 반영 대기 입력이 승인 순서대로 반영되어 새 버전이 만들어져야 한다.
- **FR-020**: 확정된 spec은 되돌릴 수 없어야 한다. 먼저 확정을 해제해야 한다.
- **FR-021**: 모든 멤버 역할(관리자, 멤버, 열람자)은 spec, 출처, 미결 질문, 버전 이력, 비교를 열람할 수 있어야 하고, 보드 비멤버는 열람할 수 없어야 한다.
- **FR-022**: 되돌리기, 확정, 해제는 관리자만 수행할 수 있어야 하며, 권한 검사는 화면 표시와 관계없이 서버 측에서 적용되어야 한다(constitution 원칙 VI).
- **FR-023**: AI 처리가 실패해도 기존 spec과 버전, 입력의 승인 상태는 변하지 않아야 하며, 실패 상태가 사용자에게 보이고 반영이 다시 시도될 수 있어야 한다.
- **FR-024**: 갱신 처리 중인 spec에는 처리 중 상태가 표시되어야 한다.
- **FR-025**: 승인된 입력이 없는 feature에서는 spec 대신 안내 문구를 보여 주어야 한다.

### Key Entities *(include if feature involves data)*

- **Spec**: feature당 하나. 현재 최신 버전, 상태(갱신 중/유휴/확정), 확정 수행자·시각을 가진다.
- **Spec 버전(SpecVersion)**: 번호, 내용(항목 목록과 미결 질문), 생성 시각, 생성 방식(AI 갱신/되돌리기), 되돌림 대상 버전, 수행 관리자, 변경 근거 입력 목록을 가진다. 한 번 만들어지면 바뀌지 않는다.
- **Spec 항목(SpecItem)**: 버전에 속하는 결정 또는 요구사항 한 건. 하나 이상의 출처 입력과 연결된다.
- **미결 질문(OpenQuestion)**: 버전에 속하는 질문. 열림/해소 상태와 해소한 입력(출처)을 가진다.
- **입력(Input)**: 001-input-approval에서 정의된 승인·대기·반려 입력. 이 feature에서는 승인된 입력만 재료로 쓰이며, 각 입력은 "반영됨/반영 대기" 상태를 추가로 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 입력 승인 후 95% 이상의 경우 2분 이내에 새 spec 버전이 열람 가능해진다.
- **SC-002**: 모든 spec 항목의 100%가 하나 이상의 출처 입력과 연결되어 있다.
- **SC-003**: 대기 또는 반려 입력의 내용이 spec 어느 버전에도 반영되는 경우가 0건이다.
- **SC-004**: 입력에 없는 세부 내용을 단정적으로 채운 항목이 0건이고, 정보가 부족한 사항은 모두 미결 질문으로 나타난다.
- **SC-005**: 팀원이 spec 항목의 출처를 확인하는 데 클릭 두 번 이내로 끝낼 수 있다.
- **SC-006**: 되돌리기를 포함한 모든 변경 후에도 이전 버전이 100% 보존된다.
- **SC-007**: 관리자가 이전 버전으로 되돌리는 데 클릭 세 번 이내로 끝낼 수 있다.
- **SC-008**: 확정된 spec에서 확정 해제 전까지 새 버전이 만들어지는 경우가 0건이다.
- **SC-009**: 권한 없는 동작(멤버·열람자의 되돌리기·확정·해제, 비멤버의 열람) 시도가 100% 거부된다.

## Assumptions

- 입력 제출과 승인은 001-input-approval에서 제공된다고 전제하며, 이 feature는 그 feature의 승인된 입력 조회를 재료로 사용한다.
- spec 문서의 구조는 항목(결정·요구사항)과 미결 질문으로 구성된다. 세부 서식은 plan 단계에서 정한다.
- 한 feature에서 AI 갱신은 한 번에 하나씩만 처리하며, 동시에 승인된 입력은 승인 순서대로 차례로 처리된다.
- 되돌리기 이전에 반영되었던 입력은 되돌린 뒤 자동으로 재반영되지 않는다.
- 미결 질문의 해소는 AI가 승인된 입력에서 답을 찾은 경우에만 일어나며, 사람이 질문을 직접 닫는 기능은 범위 밖이다.
- spec을 사람이 직접 편집하는 기능은 범위 밖이다. 변경은 입력(AI 갱신)과 되돌리기로만 이루어진다.
- 알림(이메일 등)은 범위 밖이며, 상태는 화면에서 확인한다.
- 새 입력과 확정된 결정의 충돌 경고, spec 마크다운 내보내기, 실시간 공동 편집은 별도 feature에서 다룬다.
- 단일 팀(보드 하나)을 우선 지원한다.
