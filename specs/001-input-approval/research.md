# Research: 입력 제출과 관리자 승인

| 결정 | 선택 | 근거 | 검토한 대안 |
|---|---|---|---|
| 앱 구조 | Next.js 풀스택 단일 프로젝트 | 소규모 팀의 화면 약 5개, 타입을 서버·화면이 공유, 배포 단순 | 프론트(React)+백엔드(NestJS) 분리: 이 규모에서 오버헤드 |
| DB | PostgreSQL | 상태 전이의 조건부 갱신과 제약(부분 유니크, 체크)을 DB에서 보장 | SQLite: 이후 동시 접근·확장에 불리 |
| ORM | Prisma | 스키마가 곧 문서, 마이그레이션 내장 | Drizzle: 가능하나 팀 숙련도 정보 없음 |
| 인증 | Auth.js Credentials(이메일·비밀번호) | 외부 IdP 없이 시작 가능. 스펙은 방식을 규정하지 않음 | 소셜 로그인: 후속 추가 가능 |
| 동시 승인/반려 | `UPDATE ... WHERE status='PENDING'` 영향 행 수로 판정 | 락 없이 "먼저 처리된 것만 적용" 보장 (엣지 케이스 1) | 낙관적 버전 컬럼: 불필요하게 복잡 |
| 마지막 관리자 보호 | 트랜잭션 안에서 관리자 수 재검사 | 동시 강등으로 관리자 0명이 되는 경쟁 방지 (FR-020) | 앱 레벨 검사만: 경쟁 조건 취약 |
| 입력 불변성 | 내용 컬럼은 갱신 API 없음, 상태 컬럼만 전이 | 근거 기록의 신뢰성 (원칙 I, IV) | 수정 허용: 범위 밖 |
| 본문 길이 한도 | 50,000자 | 긴 회의록 수용과 남용 방지 사이의 기본값. 변경 용이하도록 상수화 | 무제한: 저장·표시 위험 |
| 테스트 | 통합 테스트는 실제 PostgreSQL 사용 | 조건부 갱신과 제약은 모의 DB로 검증 불가 | 인메모리 모의: 핵심 규칙 미검증 |

미해결 NEEDS CLARIFICATION: 없음.
