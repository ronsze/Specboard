# Feature Specification: 입력 제출과 관리자 승인

**Feature Branch**: `001-input-approval`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "입력 제출과 관리자 승인 feature. 보드(팀) 안에서 멤버가 입력(회의록, 단편 아이디어, 의견)을 feature에 제출하면 \"대기\" 상태가 되고, 관리자가 승인하거나 사유와 함께 반려한다. 관리자가 직접 낸 입력은 자동 승인된다. 승인된 입력만 이후 AI spec 생성·갱신의 재료가 된다. 권한: 관리자(승인·반려·멤버 관리), 멤버(제출·열람), 열람자(열람). 반려된 입력은 사유와 함께 기록으로 남는다. 입력은 회의록일 수도 있고 짧은 아이디어 한 줄일 수도 있다. AI spec 생성, 충돌 경고, 버전 이력은 이 feature 범위가 아니다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 멤버가 입력을 제출한다 (Priority: P1)

보드의 멤버가 특정 feature에 회의록, 단편 아이디어, 의견 중 하나를 입력으로 제출한다. 제출된 입력은 즉시 반영되지 않고 "대기" 상태가 된다. 입력은 회의록처럼 긴 글일 수도, 아이디어 한 줄일 수도 있다.

**Why this priority**: 모든 후속 흐름(승인, AI spec 작성)의 출발점이다. 이것만 있어도 팀의 논의 내용이 feature별 기록으로 쌓이기 시작한다.

**Independent Test**: 멤버 계정으로 feature에 입력을 제출하고, 대기 상태로 목록에 나타나는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 멤버가 feature 화면에 있다, **When** 입력 종류(회의록/아이디어/의견)를 고르고 내용을 제출한다, **Then** 입력이 "대기" 상태로 저장되고 제출자와 제출 시각이 기록된다.
2. **Given** 멤버가 한 줄짜리 아이디어를 제출한다, **When** 제출한다, **Then** 길이 때문에 거부되지 않고 대기 상태로 저장된다.
3. **Given** 내용이 비어 있다, **When** 제출을 시도한다, **Then** 제출이 거부되고 이유가 표시된다.

---

### User Story 2 - 관리자가 입력을 승인하거나 반려한다 (Priority: P1)

관리자가 대기 중인 입력 목록을 보고 각 입력을 승인하거나, 사유를 적어 반려한다. 승인된 입력만 이후 AI spec 작성의 재료가 된다. 반려된 입력은 사유와 함께 기록으로 남는다.

**Why this priority**: 승인 없이는 어떤 입력도 반영되지 않는 것이 이 제품의 핵심 통제 방식이다.

**Independent Test**: 대기 입력을 만든 뒤 관리자가 승인한 것과 반려한 것이 각각 올바른 상태와 기록을 갖는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 대기 입력이 있다, **When** 관리자가 승인한다, **Then** 상태가 "승인"으로 바뀌고 승인자와 승인 시각이 기록된다.
2. **Given** 대기 입력이 있다, **When** 관리자가 사유를 입력하고 반려한다, **Then** 상태가 "반려"로 바뀌고 사유, 반려자, 반려 시각이 기록된다.
3. **Given** 관리자가 반려를 시도한다, **When** 사유가 비어 있다, **Then** 반려가 거부된다.
4. **Given** 멤버가 제출한 입력이 반려되었다, **When** 제출자가 입력 목록을 본다, **Then** 반려 상태와 사유를 확인할 수 있다.

---

### User Story 3 - 관리자가 낸 입력은 자동 승인된다 (Priority: P2)

관리자가 직접 제출한 입력은 대기 단계 없이 곧바로 "승인" 상태가 된다.

**Why this priority**: 관리자가 자기 입력을 스스로 승인하는 불필요한 절차를 없앤다. 흐름의 핵심은 아니므로 P2다.

**Independent Test**: 관리자 계정으로 입력을 제출하고 즉시 승인 상태인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 관리자가 feature 화면에 있다, **When** 입력을 제출한다, **Then** 입력이 곧바로 "승인" 상태로 저장되고 자동 승인임이 기록에 표시된다.

---

### User Story 4 - 역할별 권한이 적용된다 (Priority: P2)

보드 안에서 사용자는 관리자, 멤버, 열람자 중 하나의 역할을 갖고, 역할에 따라 할 수 있는 일이 제한된다. 관리자는 멤버의 역할을 관리한다.

**Why this priority**: 승인 구조가 의미를 가지려면 아무나 승인하거나 제출할 수 없어야 한다.

**Independent Test**: 세 역할의 계정으로 각각 제출, 승인, 열람을 시도해 허용과 거부가 기대대로인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 열람자 계정이다, **When** 입력 제출을 시도한다, **Then** 거부된다.
2. **Given** 멤버 계정이다, **When** 입력을 승인하거나 반려하려 한다, **Then** 거부된다.
3. **Given** 관리자 계정이다, **When** 보드 멤버의 역할을 변경한다, **Then** 변경 이후부터 새 역할의 권한이 적용된다.
4. **Given** 보드에 속하지 않은 사용자이다, **When** 그 보드의 입력을 열람하려 한다, **Then** 거부된다.

---

### Edge Cases

- 두 관리자가 같은 대기 입력을 동시에 승인/반려하면, 먼저 처리된 결과만 적용되고 나중 관리자에게는 이미 처리되었다고 알린다.
- 이미 승인 또는 반려된 입력은 다시 처리할 수 없다.
- 제출자가 입력을 제출한 뒤 역할이 열람자로 낮아져도 이미 제출된 입력은 유지된다.
- 대기 중인 입력의 제출자가 보드에서 제거되어도 입력과 제출자 표시는 기록으로 남는다.
- 매우 긴 회의록도 제출할 수 있어야 하며, 허용 길이를 넘으면 한도를 안내하며 거부한다.
- 관리자가 보드에 한 명뿐인 경우, 그 관리자의 역할을 낮추는 변경은 거부된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 멤버와 관리자가 feature에 입력을 제출할 수 있어야 한다.
- **FR-002**: 입력은 종류(회의록, 아이디어, 의견) 중 하나를 가져야 한다.
- **FR-003**: 아이디어 한 줄처럼 짧은 입력도 유효한 입력으로 받아야 한다.
- **FR-004**: 빈 입력은 거부해야 한다.
- **FR-005**: 멤버가 제출한 입력은 "대기" 상태로 저장되어야 한다.
- **FR-006**: 관리자가 제출한 입력은 "승인" 상태로 저장되고, 자동 승인임을 기록해야 한다.
- **FR-007**: 관리자는 대기 입력을 승인할 수 있어야 하며, 승인자와 시각이 기록되어야 한다.
- **FR-008**: 관리자는 대기 입력을 반려할 수 있어야 하며, 반려 사유는 필수이고 반려자와 시각이 기록되어야 한다.
- **FR-009**: 승인 또는 반려가 끝난 입력은 다시 처리할 수 없어야 한다.
- **FR-010**: 승인된 입력만 "AI spec 작성에 사용 가능한 입력"으로 구분되어야 한다. 대기와 반려 입력은 사용 가능 대상에서 제외되어야 한다.
- **FR-011**: 반려된 입력은 사유와 함께 삭제되지 않고 기록으로 남아야 하며, 제출자와 관리자가 볼 수 있어야 한다.
- **FR-012**: 사용자는 보드 안에서 관리자, 멤버, 열람자 중 하나의 역할을 가져야 한다.
- **FR-013**: 관리자는 보드 멤버의 역할을 지정하고 변경할 수 있어야 한다.
- **FR-014**: 열람자는 입력을 열람만 할 수 있고, 제출·승인·반려는 할 수 없어야 한다.
- **FR-015**: 멤버는 입력을 제출하고 열람할 수 있으나 승인·반려는 할 수 없어야 한다.
- **FR-016**: 권한 검사는 화면 표시 여부와 관계없이 서버 측에서 적용되어야 한다(constitution 원칙 VI).
- **FR-017**: 보드에 속하지 않은 사용자는 그 보드의 입력을 열람할 수 없어야 한다.
- **FR-018**: 관리자는 feature별 대기 입력 목록을 한 화면에서 볼 수 있어야 한다.
- **FR-019**: 모든 입력은 제출자, 제출 시각, 종류, 상태를 보여 주어야 한다.
- **FR-020**: 보드에는 관리자가 항상 한 명 이상 있어야 한다.

### Key Entities *(include if feature involves data)*

- **보드(Board)**: 팀 단위의 공간. 멤버와 각자의 역할을 가진다.
- **멤버 역할(Role)**: 보드 안에서 사용자가 가지는 관리자, 멤버, 열람자 중 하나.
- **feature**: 입력이 제출되는 대상. 하나의 보드의 프로젝트에 속한다.
- **입력(Input)**: 종류(회의록/아이디어/의견), 내용, 제출자, 제출 시각, 상태(대기/승인/반려)를 가진다. 승인 시 승인자·시각·자동 승인 여부, 반려 시 반려자·시각·사유가 추가된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 멤버가 입력을 제출하는 데 30초 이내(내용 작성 시간 제외)에 완료할 수 있다.
- **SC-002**: 관리자가 대기 입력 하나를 승인하는 데 클릭 두 번 이내로 끝낼 수 있다.
- **SC-003**: 대기 또는 반려 상태의 입력이 AI spec 작성 재료로 사용 가능한 목록에 포함되는 경우가 0건이다.
- **SC-004**: 권한 없는 동작(열람자의 제출, 멤버의 승인 등) 시도가 100% 거부된다.
- **SC-005**: 반려된 모든 입력에 사유가 기록되어 있고, 제출자가 이를 열람할 수 있다.
- **SC-006**: 관리자가 낸 입력은 100% 대기 단계 없이 승인 상태로 저장된다.

## Assumptions

- 사용자 계정과 로그인은 이 feature에서 사용할 수 있는 상태로 전제한다(방식은 plan 단계에서 결정).
- 보드, 프로젝트, feature의 생성과 구조는 이 feature의 범위 밖이며, 입력을 붙일 feature가 이미 존재한다고 전제한다. 보드 멤버 초대와 역할 지정만 이 feature에 포함한다.
- 사용자는 한 보드 안에서 하나의 역할만 가진다.
- 승인 또는 반려 이후에는 입력 내용을 수정할 수 없다. 대기 중 입력의 수정·철회는 이 feature의 범위 밖이다.
- 입력은 텍스트만 지원한다. 파일 첨부는 범위 밖이다.
- 알림(이메일 등)은 범위 밖이며, 상태는 화면에서 확인한다.
- AI spec 생성, 충돌 경고, spec 버전 이력은 별도 feature에서 다룬다.
- 단일 팀(보드 하나)을 우선 지원한다.
