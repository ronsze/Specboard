# Feature Specification: 충돌 경고

**Feature Branch**: `004-conflict-warnings`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "충돌 경고 feature. 멤버가 새 입력을 제출하면 AI가 그 입력을 feature의 현재 spec 항목(특히 확정된 spec의 결정·요구사항)과 비교해, 어긋날 수 있는 항목을 찾아 관리자의 승인 화면에 경고로 보여준다. 경고는 참고용이며 승인·반려를 막지 않는다. 경고에는 충돌 가능성이 있는 항목의 번호와 문구, 한 줄 이유, 입력 원문 중 근거가 된 문장 발췌를 포함한다. 발췌는 서버가 원문에 실제로 있는지 확인하고 없으면 이유만 보여준다. 경고 대상 항목은 현재 최신 버전에 실제로 존재해야 한다. 경고는 관리자 승인 화면에만 보이고 제출자와 열람자에게는 보이지 않는다. 관리자는 경고를 확인했다고 닫을 수 있고(승인과 별개) 닫은 기록은 남는다. 입력이 승인·반려되어도 경고는 처리됨 상태로 남는다. 검사는 제출 후 비동기로 수행되며 검사 중·완료(경고 있음/없음)·실패 상태가 보이고, 실패해도 제출·승인에 영향이 없으며 관리자가 다시 검사할 수 있다. 확정되지 않은 spec과도 비교하되 확정된 spec과의 충돌을 더 눈에 띄게 표시한다. spec이 없는 feature는 검사 없이 경고 없음으로 처리한다. 자동 반려, 대기 입력끼리의 충돌 검사, 승인된 입력의 사후 재검사, 알림, 마크다운 내보내기는 범위 밖이다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자가 승인하기 전에 기존 결정과 어긋날 수 있는 입력을 알아챈다 (Priority: P1)

관리자가 승인 대기 화면에서 입력을 검토할 때, 그 입력이 기존 spec의 어떤 항목과 어긋날 수 있는지가 입력 카드 안에 경고로 보인다. 경고에는 충돌 가능성이 있는 항목의 번호와 문구, 어긋난다고 보는 한 줄 이유, 입력 원문 중 근거가 된 문장이 들어 있다. 확정된 spec의 항목과 충돌할 수 있는 경우는 더 눈에 띄게 표시된다. 경고는 참고용이라 승인·반려를 막지 않는다.

**Why this priority**: 팀의 결정이 나중에 충돌하는 것을 막는다는 이 제품의 존재 이유를 직접 수행한다. 승인 전에 알아채야 효과가 있다.

**Independent Test**: 확정된 spec에 "쿠폰은 주문당 한 장만 적용한다"가 있는 feature에서 "쿠폰 두 장 허용"이라는 입력을 제출하고, 관리자 승인 화면에서 해당 항목(D-1)과의 충돌 경고가 이유·발췌와 함께 보이며 승인도 가능한지 확인한다.

**Acceptance Scenarios**:

1. **Given** 확정된 spec의 항목 D-1과 어긋나는 입력이 대기 중이다, **When** 관리자가 승인 대기 화면을 연다, **Then** 그 입력 카드에 "확정된 결정과 충돌 가능" 경고가 D-1의 번호와 문구, 한 줄 이유, 입력 원문 중 근거 문장과 함께 보인다.
2. **Given** 확정되지 않은 spec의 항목과 어긋나는 입력이다, **When** 관리자가 화면을 연다, **Then** 경고가 보이되 확정된 항목과의 충돌보다 덜 눈에 띄게(다른 문구와 아이콘, 강조 정도) 구분되어 표시된다.
3. **Given** 경고가 있는 입력이다, **When** 관리자가 승인하거나 사유와 함께 반려한다, **Then** 경고 때문에 처리가 막히거나 추가 확인을 요구받지 않는다.
4. **Given** 한 입력에 여러 항목과의 충돌 가능성이 있다, **When** 카드를 본다, **Then** 항목마다 따로 경고가 보이고, 같은 항목에 대한 경고는 중복되지 않는다.
5. **Given** 충돌 가능성이 없다고 판단된 입력이다, **When** 카드를 본다, **Then** "충돌 가능성 없음"이라는 검사 완료 표시가 보인다.
6. **Given** 입력이 기존 항목과 어긋나지 않고 열려 있는 미결 질문에 답하는 내용이다, **When** 검사가 끝난다, **Then** 충돌로 표시되지 않는다.

### User Story 2 - 입력을 제출하면 검사가 자동으로 수행되고 상태가 보인다 (Priority: P1)

멤버가 입력을 제출하면 검사가 자동으로 시작되고, 관리자는 승인 화면에서 검사 중, 완료(경고 있음/없음), 실패 중 어느 상태인지 볼 수 있다. spec이 아직 없는 feature의 입력은 비교할 대상이 없어 검사 없이 "경고 없음"으로 처리된다. 검사는 입력 제출이나 승인 속도에 영향을 주지 않는다.

**Why this priority**: 경고가 자동으로 만들어지고 신뢰할 수 있게 상태가 드러나야 승인 흐름에 쓸 수 있다.

**Independent Test**: spec이 있는 feature와 없는 feature에 각각 입력을 제출하고, 상태가 검사 중 → 완료로 바뀌는지, spec 없는 쪽은 즉시 경고 없음인지 확인한다.

**Acceptance Scenarios**:

1. **Given** spec이 있는 feature에서 멤버가 입력을 제출한다, **When** 제출이 끝난다, **Then** 제출은 즉시 완료되고 입력은 "대기" 상태가 되며, 관리자 화면에는 "검사 중" 표시가 보이다가 결과(경고 있음 또는 없음)로 바뀐다.
2. **Given** spec이 없는 feature에서 입력을 제출한다, **When** 관리자가 승인 화면을 본다, **Then** 검사 없이 "비교할 spec 없음 · 경고 없음"으로 표시된다.
3. **Given** 검사가 실패했다, **When** 관리자가 승인 화면을 본다, **Then** "검사 실패" 표시와 다시 검사하는 동작이 보이고, 그 입력을 승인·반려하는 데는 아무 영향이 없다.
4. **Given** 관리자가 직접 제출해 자동 승인된 입력이다, **When** 화면을 본다, **Then** 검사 대상이 아니므로 검사 표시가 없다.

---

### User Story 3 - 관리자가 경고를 확인했다고 닫고 기록을 남긴다 (Priority: P2)

관리자가 경고를 검토한 뒤 "확인함"으로 닫을 수 있다. 닫아도 승인·반려와는 무관하며, 누가 언제 닫았는지가 기록으로 남는다. 닫은 경고는 접힌 상태로 남아 다시 볼 수 있다.

**Why this priority**: 경고를 읽고도 승인했다는 책임 있는 기록이 남고, 여러 관리자가 같은 경고를 반복해서 보지 않게 한다.

**Independent Test**: 경고가 있는 입력에서 경고를 닫고, 닫은 사람·시각이 보이며 입력은 여전히 대기 상태이고 경고를 다시 펼쳐볼 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 열린 경고가 있다, **When** 관리자가 "확인함"을 누른다, **Then** 경고가 접힌 "확인됨" 상태가 되고 확인한 관리자와 시각이 기록되며 입력의 대기·승인 상태는 바뀌지 않는다.
2. **Given** 확인된 경고이다, **When** 관리자가 펼친다, **Then** 이유와 발췌, 확인자·시각이 그대로 보인다.
3. **Given** 승인 대기 배지나 목록에서, **When** 경고를 모두 확인한 입력이 있다, **Then** 그 입력은 "경고 확인됨"으로 구분된다. 승인 대기 목록에 남아 있는 것은 입력이 아직 승인되지 않았기 때문이다.
4. **Given** 멤버 또는 열람자이다, **When** 경고를 닫으려 한다, **Then** 허용되지 않는다.

---

### User Story 4 - 처리된 입력의 경고가 이력으로 남는다 (Priority: P2)

입력이 승인되거나 반려된 뒤에도 그 입력에 붙었던 경고와 관리자의 확인 기록이 "처리됨"으로 남아, feature의 입력 화면(관리자 보기)에서 확인할 수 있다. 나중에 "왜 이 입력이 승인되었는데 기존 결정과 충돌했나"를 추적할 수 있다.

**Why this priority**: 사후 책임 추적과 충돌 원인 분석에 필요하나, 승인 전 경고(P1)가 먼저다.

**Independent Test**: 경고가 있던 입력을 승인한 뒤 입력 화면의 관리자 보기에서 경고가 처리됨 상태로 남아 있는지, 멤버 화면에서는 보이지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 경고가 있던 입력이 승인되었다, **When** 관리자가 feature 입력 화면을 본다, **Then** 그 카드에 경고가 "처리됨(승인됨)"으로 남아 보인다.
2. **Given** 경고가 있던 입력이 반려되었다, **When** 관리자가 입력 화면을 본다, **Then** 경고가 "처리됨(반려됨)"으로 남아 보인다.
3. **Given** 처리된 입력이다, **When** 멤버·열람자·제출자가 같은 입력 화면을 본다, **Then** 경고와 검사 상태는 어디에도 보이지 않는다.

---

### User Story 5 - 관리자가 검사를 다시 시도한다 (Priority: P2)

AI 호출 실패 등으로 검사가 실패했거나, 검사 안 함으로 처리되었거나, 검사 뒤에 spec이 갱신되어 결과가 낡은 대기 입력은 관리자가 최신 spec 기준으로 다시 검사할 수 있다. 다시 검사하면 새 결과가 최신 결과로 표시되고 이전 결과는 기록으로 남는다.

**Why this priority**: 일시적 실패나 낡은 결과 때문에 경고 없는 입력이 그대로 승인되는 것을 관리자가 스스로 막을 수 있게 한다.

**Independent Test**: 검사를 실패시킨 뒤 관리자가 다시 검사하여 결과가 최신으로 바뀌는지, 멤버는 다시 검사할 수 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 검사가 실패한 대기 입력이다, **When** 관리자가 "다시 검사"를 누른다, **Then** 상태가 "검사 중"이 되고 끝나면 새 결과가 표시된다.
2. **Given** 검사가 성공했고 그 뒤로 spec이 바뀌지 않았거나, 입력이 이미 승인·반려되었거나, 검사가 진행 중이다, **When** 다시 검사를 시도한다, **Then** 허용되지 않고 이유가 안내된다.
3. **Given** 검사가 끝난 뒤 spec이 새 버전으로 갱신되었다(또는 spec이 없을 때 제출된 입력인데 그 뒤 spec이 생겼다), **When** 관리자가 그 대기 입력을 본다, **Then** "검사 이후 spec이 vN으로 갱신됨" 안내와 함께 최신 spec 기준으로 "다시 검사"할 수 있다.
4. **Given** 검사 결과 카드이다, **When** 관리자가 본다, **Then** 그 검사가 비교에 쓴 spec 버전("v3 기준")이 표시된다.
5. **Given** 멤버 또는 열람자이다, **When** 다시 검사를 시도한다, **Then** 허용되지 않는다.

---

### Edge Cases

- 검사 중에 관리자가 그 입력을 승인·반려하면 검사는 계속 끝까지 수행되어 결과가 "처리됨" 상태로 남는다.
- 검사가 진행되는 동안 spec에 새 버전이 생기거나 되돌리기·확정·해제가 일어나면, 결과를 저장하는 시점의 최신 버전을 기준으로 경고 대상 항목이 실제로 존재하는지 확인하고, 더 이상 존재하지 않는 항목을 가리키는 경고는 저장하지 않는다.
- 확정 여부는 경고를 만든 시점의 상태를 기록하며, 이후 확정이 해제되어도 이미 만든 경고의 표시("확정된 결정과 충돌 가능")는 바뀌지 않고 그 시점 기준임이 보인다.
- 한 입력에 대한 경고는 최대 5개까지 표시하고, 같은 항목에 대한 경고는 하나만 둔다.
- AI가 제시한 발췌가 입력 원문에 없으면 발췌 없이 이유만 보여주고 경고 자체는 유지한다.
- 항목이 매우 많은 spec이어도 검사가 가능해야 하며, 비교 대상은 검사 시점 최신 버전의 항목 전체다. 너무 커서 처리할 수 없으면 검사 실패로 표시하고 이유를 알린다.
- 다시 검사하면 이전에 확인한 경고와 같은 항목에 대한 경고가 새로 만들어질 수 있으며, 이 경우 새 경고는 확인되지 않은 상태로 시작한다. 이전 검사 결과와 확인 기록은 남는다.
- 입력이 열려 있는 미결 질문에 답하는 내용이면 충돌로 보지 않는다.
- 반영 대기 중인 승인 입력(아직 spec에 반영되지 않음)은 비교 대상이 아니다. 비교 대상은 spec에 실제로 있는 항목이다.
- 검사는 입력당 제출 시 한 번만 자동으로 수행되며(이후는 관리자가 수동으로 다시 검사), 같은 입력에 대해 동시에 두 검사가 진행되지 않는다.
- spec이 없을 때 제출되어 검사 안 함으로 처리된 대기 입력은, 그 뒤 spec의 첫 버전이 생기면 "다시 검사"할 수 있다. 자동으로 다시 검사하지는 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 멤버가 입력을 제출하면 시스템은 그 입력에 대한 충돌 검사를 자동으로 시작해야 한다. 검사는 제출과 비동기로 수행되어 제출과 승인의 속도에 영향을 주어서는 안 된다.
- **FR-002**: 검사는 그 입력을 검사 시점 feature의 spec 최신 버전의 항목 전체와 비교해 어긋날 수 있는 항목을 찾아야 한다.
- **FR-003**: 각 경고는 충돌 가능성이 있는 항목의 번호(D-n/R-n)와 문구, 어긋난다고 보는 이유(한 줄), 입력 원문 중 근거가 된 문장 발췌를 포함해야 한다.
- **FR-004**: 시스템은 AI가 제시한 발췌가 입력 원문에 실제로 있는지 확인해야 하며(공백·줄바꿈 차이는 무시), 있는 것만 저장·표시하고 없으면 발췌 없이 이유만 보여주어야 한다. 발췌가 없다는 이유로 경고를 버려서는 안 된다.
- **FR-005**: 경고 대상 항목은 결과를 저장하는 시점의 spec 최신 버전에 실제로 존재해야 하며, 존재하지 않는 항목을 가리키는 경고는 저장해서는 안 된다.
- **FR-006**: 한 입력의 경고는 최대 5개이고, 같은 항목에 대한 경고는 하나여야 한다.
- **FR-007**: 경고는 그것을 만든 시점에 대상 항목이 확정된 spec에 속했는지 여부를 기록하고, 확정된 spec의 항목과의 충돌은 그렇지 않은 경우와 구별되게(문구, 아이콘, 강조 정도) 더 눈에 띄게 표시해야 한다.
- **FR-008**: 경고는 참고용이다. 경고가 있어도 승인과 반려는 추가 확인 없이 평소와 같이 수행되어야 한다.
- **FR-009**: 열려 있는 미결 질문에 답하는 내용은 충돌로 표시되어서는 안 된다.
- **FR-010**: spec이 아직 없는 feature의 입력은 검사 없이 "비교할 spec 없음 · 경고 없음"으로 처리되어야 한다.
- **FR-011**: 관리자가 직접 제출해 자동 승인된 입력은 검사 대상이 아니다.
- **FR-012**: 검사 상태는 검사 중, 완료(경고 있음), 완료(경고 없음), 실패, 검사 안 함(spec 없음)으로 구분되어 승인 화면의 입력 카드에 표시되어야 하며, 각 상태는 색뿐 아니라 아이콘과 글자로도 구분되어야 한다.
- **FR-013**: 검사가 실패해도 입력의 제출, 승인, 반려는 영향을 받아서는 안 된다. 실패 상태에는 실패했음을 알리는 안내가 보여야 한다.
- **FR-014**: 관리자는 대기 상태의 입력에 대해, 최신 결과가 실패이거나 검사 안 함이거나 기준 spec 버전이 현재 spec 최신 버전보다 낮은(낡은) 경우에 검사를 다시 시도할 수 있어야 한다. 이미 처리된 입력, 진행 중인 검사, 최신 spec 기준으로 성공한 검사에는 다시 시도할 수 없다.
- **FR-015**: 다시 검사하면 새 결과가 최신 결과로 표시되고, 이전 검사 결과와 관리자의 확인 기록은 남아야 한다.
- **FR-016**: 관리자는 경고를 "확인함"으로 닫을 수 있어야 한다. 닫는 동작은 입력의 승인·반려 상태에 영향을 주지 않으며, 확인한 관리자와 시각이 기록되어야 한다.
- **FR-017**: 확인된 경고는 접힌 상태로 남아 이유, 발췌, 확인자·시각을 다시 볼 수 있어야 한다.
- **FR-018**: 입력이 승인 또는 반려되면 그 입력의 경고와 검사 상태는 "처리됨(승인됨/반려됨)"으로 남아야 하며, 관리자는 feature 입력 화면에서 이를 볼 수 있어야 한다.
- **FR-019**: 검사 상태와 경고는 관리자에게만 보여야 한다. 멤버, 열람자, 입력을 제출한 본인에게도 보여서는 안 되며, 이 제한은 화면 표시와 관계없이 서버 측에서 적용되어야 한다(constitution 원칙 VI).
- **FR-020**: 경고 확인과 다시 검사는 관리자만 수행할 수 있어야 하며 서버 측에서 검사되어야 한다.
- **FR-021**: 입력이 승인·반려된 뒤에도 진행 중이던 검사는 끝까지 수행되어 결과가 처리됨 상태로 남아야 한다.
- **FR-022**: 승인되어 이미 spec에 반영된 입력의 사후 재검사, 대기 입력끼리의 충돌 검사, 자동 반려, 알림은 제공하지 않는다.
- **FR-023**: 보드 단위 승인 대기 화면과 feature 입력 화면의 관리자 보기 모두에서 같은 경고 표시를 보여야 한다. 시안의 "예정" 자리를 실제 기능으로 대체한다.
- **FR-025**: 검사 결과에는 그 검사가 비교에 쓴 spec 버전이 표시되어야 하고, 그 뒤 spec이 새 버전으로 갱신되었으면 관리자에게 "검사 이후 spec이 vN으로 갱신됨"이 안내되어야 한다.
- **FR-024**: 보드 단위 승인 대기 목록에서 관리자는 경고가 있는 입력과 아직 확인하지 않은 경고의 개수를 알아볼 수 있어야 한다.

### Key Entities *(include if feature involves data)*

- **충돌 검사(ConflictCheck)**: 입력 하나에 대한 검사 한 번의 기록. 상태(검사 중, 완료, 실패, 검사 안 함), 검사에 쓴 spec 버전, 시도 횟수, 시작·완료 시각, 실패 사유를 가진다. 입력당 여러 번(다시 검사) 있을 수 있고 가장 최근 것이 현재 결과다.
- **충돌 경고(ConflictWarning)**: 한 검사가 찾아낸 충돌 가능성 한 건. 대상 항목(번호와 검사 시점 문구), 확정된 spec의 항목이었는지 여부, 이유, 입력 원문 중 발췌 구간(없을 수 있음), 확인 상태(열림/확인됨)와 확인한 관리자·시각을 가진다.
- **입력(Input)**: 001에서 정의된 입력. 이 feature에서는 최신 검사 결과를 조회할 수 있어야 한다.
- **Spec 항목(SpecItem)**: 002·003에서 정의된 항목. 경고는 항목의 안정 번호(D-n/R-n)로 가리킨다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 멤버가 입력을 제출한 뒤 95% 이상의 경우 1분 이내에 승인 화면에 검사 결과(경고 있음/없음/실패 중 하나)가 표시된다.
- **SC-002**: 입력 제출과 승인·반려는 검사의 성공·실패·지연과 무관하게 100% 정상 수행된다(검사 때문에 막히는 경우 0건).
- **SC-003**: 저장되거나 표시되는 경고 중 최신 버전에 존재하지 않는 항목을 가리키는 것이 0건이다.
- **SC-004**: 표시되는 인용 발췌의 100%가 입력 원문에 실제로 존재하는 문장이다.
- **SC-005**: 검사 상태와 경고가 멤버, 열람자, 제출자에게 노출되는 경우가 0건이고, 이를 시도하는 요청이 100% 거부된다.
- **SC-006**: 확정된 spec 항목과의 충돌 경고는 다른 경고와 100% 구별되어 표시된다(아이콘·문구 모두 다름).
- **SC-007**: 관리자가 경고를 확인 처리하는 데 클릭 두 번 이내가 걸리고, 확인자와 시각이 100% 기록된다.
- **SC-008**: 승인·반려된 입력의 경고 이력이 100% 보존되어 관리자가 입력 화면에서 확인할 수 있다.
- **SC-010**: 검사가 낡은 대기 입력(검사 이후 spec이 갱신됨, 또는 spec 없이 제출됨)의 100%에 낡았다는 안내와 다시 검사 동작이 표시된다.
- **SC-009**: 시연용 충돌 입력 세트(확정 항목과 모순되는 입력 5건, 모순 없는 입력 5건)에서 모순 입력의 80% 이상에 경고가 달리고, 모순 없는 입력의 경고(오탐)는 20% 이하다.

## Assumptions

- 비교 대상은 검사 시점의 spec 최신 버전 항목이다. 반영 대기 중인 승인 입력은 아직 spec에 없으므로 비교하지 않는다.
- 확정된 spec과 확정되지 않은 spec의 구분은 경고를 만든 시점의 상태로 기록하며, 이후 확정 해제 여부로 경고가 바뀌지 않는다.
- 다시 검사는 새 검사 기록을 만들고, 화면에는 가장 최근 검사 결과만 현재 결과로 표시한다. 이전 검사 결과와 확인 기록은 보존되지만 화면에는 기본으로 보이지 않는다.
- 경고 확인(닫기)은 승인 흐름의 필수 단계가 아니며, 확인하지 않고도 승인할 수 있다.
- 검사는 입력당 제출 시 한 번 자동으로 수행된다. 입력은 수정되지 않으므로 입력 변경에 따른 재검사는 없으며, spec이 갱신되어 결과가 낡은 경우는 관리자가 수동으로 다시 검사한다(자동 재검사 없음).
- AI 검사는 완전하지 않다. 놓침과 오탐이 있을 수 있으며, 경고는 관리자 판단을 돕는 참고 정보로만 사용한다(자동 반려 없음).
- 검사 AI의 구체적인 모델과 호출 방식은 plan 단계에서 정한다. 비용을 줄이기 위해 검사 대상 입력의 길이와 비교 항목 수에 상한이 필요하면 plan 단계에서 정하고, 상한을 넘으면 검사 실패(사유 안내)로 처리한다.
- 경고에 쓰는 항목 번호와 발췌 표시는 003의 번호 체계와 발췌 검증 규칙을 재사용한다.
- 단일 팀(보드 하나)을 우선 지원한다. 입력 간 충돌, 사후 재검사, 알림, spec 마크다운 내보내기는 별도 feature에서 다룬다.
